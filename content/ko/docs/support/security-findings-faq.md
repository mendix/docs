## 소개

이 문서에서는 보안 발견 사항 및 Mendix 제품과 플랫폼의 보안에 관해 자주 받는 질문(FAQ)을 나열합니다.
보안 티켓을 생성하려면 *지원 요청 제출*의 [보안 지원 티켓 요구 사항](/support/submit-support-request/#security-tickets) 섹션을 참조하십시오.

Mendix 플랫폼의 다른 곳에서도 보안 및 보고된 취약점에 대한 추가 정보를 확인할 수 있습니다. 아래 섹션의 링크를 참조하십시오.

### 현재 보안 이슈

이 FAQ 문서는 실시간으로 업데이트되지 않습니다. 현재 보안 이슈에 대한 업데이트는 [Mendix 상태 페이지: https://status.mendix.com/](https://status.mendix.com/)를 참조하십시오.

### 보안 권고

Mendix 보안 권고는 [보안 권고](/releasenotes/security-advisories/)에 게시됩니다.

### 일반 보안 조언

앱을 안전하게 만드는 모범 사례는 [앱 보안 모범 사례 구현 방법](/howto/security/best-practices-security/)에서 확인하실 수 있습니다.

### 규정 준수 보고서

SOC, ISO, PCI 등 Mendix의 규정 준수 보고서는 Mendix 고객 및 잠재 고객에게 [Conveyor의 Mendix 프로필](https://app.conveyor.com/profile/mendix)에서 제공됩니다. Mendix 계정에 사용하는 이메일 주소로 접근을 요청하면 접근 권한이 부여됩니다. 댓글에 CSM의 이름과 찾고 있는 문서를 언급하면 승인 속도를 높이는 데 도움이 될 수 있습니다.

{{% alert color="info" %}}
Mendix는 규정 준수 보고서를 공개적으로 제공하지 않습니다. 접근 승인을 받으려면 Mendix 고객 또는 잠재 고객이어야 합니다.
{{% /alert %}}

### 플랫폼 지원

Mendix 지원팀은 플랫폼에서 지원하는 구성 요소를 사용하는 경우에만 지원을 제공합니다. Mendix에서 지원하는 것과 직접 지원해야 하는 것에 대한 정보는 [다양한 배포 전략에 대한 지원](/support/deployment-strategy-support/)의 표를 참조하십시오. Marketplace 구성 요소의 경우, Marketplace에서 해당 구성 요소를 찾아 구성 요소 이름 오른쪽의 **Support** 섹션을 확인하여 지원 상태를 확인할 수 있습니다.

### 보안 연락처

Control Center에서 회사의 [보안 연락처](/control-center/company-settings/#security-contact)를 추가하고 관리할 수 있습니다. 보안 연락처는 Mendix 플랫폼 및 플랫폼 지원 Marketplace 구성 요소에 중요한 보안 이슈가 있는 경우 통보를 받습니다.

## 클라이언트에서 데이터를 조작할 수 있나요?

일반적인 우려 사항 중 하나는 최종 사용자가 브라우저 또는 기기의 도구를 사용하여 로컬에 저장된 데이터를 변경하고 이를 통해 접근할 수 없어야 하는 정보에 접근하는 것입니다. 이 섹션에서는 이러한 우려 사항을 다루고 Mendix Runtime 서버가 데이터를 어떻게 보호하는지 설명합니다.

### Mendix 보안

Mendix 애플리케이션은 두 부분으로 구성됩니다: 최종 사용자의 브라우저 또는 모바일 앱에서 실행되는 Mendix 클라이언트와 Mendix Runtime 서버입니다. 자세한 내용은 [Mendix Runtime](/refguide/runtime/)을 참조하십시오.

Mendix 클라이언트는 Mendix 클라이언트 API를 사용하여 Runtime 서버와 통신하며, Runtime 서버의 `/xas/` 요청 핸들러에 요청을 보냅니다. 클라이언트 API는 클라이언트의 요청을 안전하거나 보안적으로 신뢰할 수 없다는 전제 위에 구축되어 있습니다. 클라이언트는 서버 제어 범위 밖의 최종 사용자 기기에서 실행되므로, 데이터나 동작이 조작될 수 있습니다. "클라이언트에서 발생하는 어떤 것도 안전하다고 간주할 수 없습니다"는 Mendix 애플리케이션뿐만 아니라 클라이언트(예: 브라우저)에 저장되는 모든 것에 적용되는 원칙입니다.

따라서 Mendix에서는 올바르게 설정된 Entity 접근 규칙과 Microflow에 대한 허용된 역할을 통해 백엔드, 즉 Runtime 서버에서 항상 보안을 처리합니다. Runtime 서버는 최종 사용자가 조작할 수 없습니다.

그렇기 때문에 최종 사용자 역할에 대한 [올바른 접근 규칙을 구현](/howto/security/best-practices-security/#access-rules)하는 것이 중요합니다.

### Mendix 보안과 사용자 권한 상승

브라우저를 속여 보유하지 않은 사용자 역할을 가진 것처럼 할 수 있지만, Mendix Runtime 서버는 이를 수용하지 않습니다. 이는 모든 서버 측 데이터 및 로직이 원래 사용자 역할을 적용함을 의미합니다. 브라우저에서 사용자 역할을 변경해도 원래 사용자 역할로 접근할 수 없는 정보가 공개되지 않습니다.

### 가시성 대 보안

페이지의 경우 보안이 아닌 가시성을 설정합니다. 보안과 가시성은 두 가지 다른 것입니다. Mendix 클라이언트는 현재 최종 사용자에게 보이지 않는 페이지를 숨기며, 페이지를 여는 액션 버튼과 페이지를 직접 여는 탐색 항목도 함께 숨깁니다. 그러나 Mendix 런타임 클라이언트는 페이지에 대한 접근을 완전히 차단하지 않습니다. 최종 사용자가 보이지 않는 페이지를 여는 Microflow를 실행하거나, 딥링크를 사용하거나, 클라이언트 API를 호출하면 페이지가 여전히 표시됩니다.

Mendix 런타임이 페이지의 가시성을 제어하는 동안, 데이터에 대한 접근을 제어하기 위해 항상 보안을 사용합니다. 따라서 최종 사용자가 보이지 않는 페이지를 열 수 있더라도, 접근 권한이 있는 데이터만 해당 페이지에서 볼 수 있습니다. 최종 사용자는 접근 권한이 있는 데이터라면 항상 클라이언트 API를 사용하여 데이터를 검색할 수 있으므로, 접근 권한이 있는 데이터를 표시하는 페이지(의 일부)를 숨기는 것으로는 클라이언트 API를 통한 데이터 접근을 방지할 수 없습니다.

최종 사용자에 대해 페이지를 숨기는 것은 데이터 접근을 제한하는 방법이 아닙니다. 항상 데이터 자체에 보안을 설정해야 합니다. 가시성은 보안과 같지 않습니다.

### XPath 쿼리 조작/주입

런타임이 XPath 쿼리를 수신하면, 런타임은 항상 요청을 하는 최종 사용자의 역할에 연결된 접근 규칙을 기반으로 XPath 쿼리에 Entity 접근을 적용합니다. 따라서 최종 사용자가 XPath 쿼리를 런타임에 보내기 전에 변경할 수 있더라도, 런타임은 여전히 접근 규칙을 적용하며 최종 사용자가 접근할 수 있는 데이터만 반환합니다.

### HTTP 메시지 변조

`/xas/` 요청 핸들러는 RESTful API가 아니므로, 일반적으로 RESTful API에 적용하는 규칙이 이 경우에는 적용되지 않습니다. `/xas/` API는 사용된 HTTP 동사를 확인하지 않으며 이를 무시합니다. HTTP 메시지의 내용이 변경되더라도 보안 제한은 서버 측에서 계속 적용되며 최종 사용자는 접근 권한이 있는 데이터만 볼 수 있습니다. 아래 예시를 참조하십시오.

### 예시

예를 들어, 애플리케이션의 모든 페이지 레이아웃은 공개적으로 사용 가능한 정적 XML 페이지로 저장되어 있으므로 누구나 볼 수 있습니다. 페이지에 특정 사용자 역할에 대해 조건부로 표시되는 버튼이 있는 경우, 사용자 역할을 위조하여 이 버튼을 표시할 수 있습니다. 그러나 이 버튼을 클릭하면 데이터 검색 및 로직에 보안이 적용됩니다. 버튼이 Microflow를 트리거하는 경우, 원래 사용자 역할에 Microflow에 대한 접근 권한이 없으면 오류가 발생합니다.

Microflow가 원래 사용자 역할에서 사용 가능하지만 이를 트리거하는 버튼이 보이지 않았던 경우, 이제 Microflow를 실행할 수 있게 됩니다. 그러나 원래 사용자 역할을 사용하여 `xas` 요청을 위조하여 이를 수행할 수도 있었습니다. 따라서 이 경우 사용자 역할을 위조해도 추가 기능이 제공되지 않습니다. 최종 사용자가 접근할 수 없어야 하는 데이터를 보거나 로직을 트리거할 수 있는 경우, 이는 애플리케이션 보안이 올바르게 또는 완전하게 구성되지 않았음을 의미합니다.

## 최종 사용자가 코드 주입과 같은 악성 콘텐츠가 포함된 파일을 업로드할 수 있나요?

업로드된 파일은 서버에서 실행할 수 없습니다. 파일 관리자 Widget을 구성하여 Widget을 사용하여 업로드된 파일에 허용되는 확장자를 제한할 수 있습니다. 그러나 이는 보안 기능이 아니며, 파일 관리자 Widget은 파일의 내용이 제공된 확장자와 일치하는지 확인하지 않습니다. 자세한 내용은 [파일 관리자](/refguide/file-manager/#allowed-extensions) Widget 문서를 참조하십시오.

업로드된 파일의 악성 콘텐츠를 검사하려면 바이러스 및 맬웨어 검사를 직접 구현해야 합니다. 자세한 내용은 *앱 보안 모범 사례 구현 방법*의 [업로드된 파일의 악성 콘텐츠 검사](/howto/security/best-practices-security/#scanning-for-malicious-content) 섹션을 참조하십시오.

## 일부 Java 라이브러리에서 취약점이 보고되는 이유는 무엇인가요? {#java-libraries}

보안 검사 도구는 Java 라이브러리의 취약점을 보고할 수 있습니다. 이는 오래되고 취약한 라이브러리, 코드 또는 종속성과 같은 것일 수 있습니다. 종종 취약점은 최신 버전의 Java 라이브러리에서 해결되었습니다. Java 라이브러리의 취약점을 보고하기 전에 다음을 확인하십시오:

* jar가 플랫폼에서 지원하는 모듈에서 온 것인지 확인하십시오. 지원 카테고리에 대한 자세한 내용은 *Marketplace 개요*의 [Marketplace 콘텐츠 지원](/appstore/marketplace-content-support/) 섹션을 참조하십시오.
* 모듈이 최신 버전으로 업데이트되었는지 확인하십시오.
* userlib 폴더에서 이전 라이브러리를 제거했는지 확인하십시오. 자세한 내용은 *Marketplace 콘텐츠 사용*의 [모듈을 최신 버전으로 업데이트](/appstore/use-content/#update-module)를 참조하십시오.

### Mendix가 최신 버전의 라이브러리를 사용하지 않는 이유는 무엇인가요?

라이브러리의 새 릴리스가 반드시 해당 라이브러리의 이전 버전을 교체해야 함을 의미하지는 않습니다.

다음의 경우에만 제3자 라이브러리를 업데이트합니다:

1. 라이브러리의 새 버전에 이전 라이브러리에서 사용할 수 없는 새로운 기능이 포함된 경우 - 개발자가 업데이트된 라이브러리가 필요한 기능을 업데이트하거나 개선하는 경우, 새로 제공된 기능을 활용하기 위해 라이브러리를 업데이트합니다.
2. 이전 버전의 라이브러리에 버그가 포함된 경우 - 테스트 또는 고객이 제3자 라이브러리의 버그로 인한 플랫폼 지원 구성 요소 내의 버그를 보고하면, 버그가 해결된 버전으로 라이브러리를 업데이트합니다.
3. 이전 버전의 라이브러리에 보안 취약점이 포함된 경우 - 모든 플랫폼 지원 콘텐츠에 대해 정기적인 보안 검사를 수행하며, 보안 검사에서 제3자 라이브러리의 보안 취약점을 보고하면 보안 발견 사항을 완화하기 위해 라이브러리를 업데이트합니다.

이전 라이브러리가 필요한 모든 기능을 제공하고 버그나 보안 취약점이 없는 경우, 라이브러리를 업데이트할 필요가 없습니다. 이 경우 라이브러리를 업데이트하면 문제 발생 위험이 증가합니다: 라이브러리의 최신 버전에는 모듈 내의 기존 기능을 손상시킬 수 있는 변경 사항이 포함될 수 있습니다.

#### Marketplace 모듈의 라이브러리 버전

Mendix는 Marketplace 모듈에서 라이브러리의 주요 버전을 맞추기 위해 업데이트합니다.

## 앱의 쿠키에 일부 보안 속성이 설정되지 않은 이유는 무엇인가요?

보안 검사 도구는 Mendix가 쿠키를 처리하는 방식에서 취약점을 보고할 수 있습니다. 예를 들어 쿠키가 안전하지 않거나 취약하거나, 속성이 부적절하거나 누락된 경우입니다. 아래 섹션에서는 이러한 보고가 발생하는 이유를 설명합니다.

### 쿠키에 'Secure' 속성 누락

쿠키에 'Secure' 속성을 설정하면 클라이언트가 암호화되지 않은 통신 채널을 통해 해당 쿠키를 전송하는 것을 방지합니다. 이 설정을 지원하는 브라우저는 'Secure' 플래그가 있는 쿠키를 페이지에 보낼 때 항상 HTTPS 프로토콜을 사용합니다.

Mendix는 기본적으로 쿠키에 'Secure' 속성을 설정합니다. 유일한 예외는 "mx-cookie-test" 쿠키입니다. 이는 쿠키에 접근할 수 있는지 확인하기 위해 임시로 설정하는 쿠키입니다. Mendix는 기능을 위해 쿠키에 크게 의존하므로, 최종 사용자에게 쿠키를 활성화해야 한다는 경고를 표시할지 결정하는 데 도움이 됩니다.
자세한 내용은 *Mendix 클라이언트*의 [쿠키](/refguide/mendix-client/#cookies) 섹션을 참조하십시오.

### 쿠키에 'HTTPOnly' 속성 누락

Mendix Cloud에서는 (거의 모든) 쿠키에 기본적으로 'HttpOnly' 속성이 true로 설정되어 있습니다.
Mendix 애플리케이션에서 기본적으로 설정되는 쿠키는 *Mendix 클라이언트*의 [쿠키](/refguide/mendix-client/#cookies) 섹션에 설명되어 있습니다.

Mendix 애플리케이션의 경우, Mendix Runtime에서 설정한 쿠키에는 'HTTPOnly' 속성이 true로 설정되어 있습니다. Mendix 클라이언트에서 설정한 쿠키는 JavaScript에서 사용할 수 없게 되므로 'HttpOnly' 속성을 true로 설정할 수 없습니다. JavaScript는 Mendix 클라이언트에서 사용하는 언어입니다.

세션 ID와 같은 민감한 정보를 포함할 수 있는 Mendix Runtime에서 설정한 쿠키에는 항상 'HttpOnly' 플래그가 true로 설정되어 있습니다. 'HTTPOnly'가 false로 설정된 Mendix 클라이언트에서 설정한 쿠키에는 민감한 정보가 포함되지 않습니다.

## 앱에 일부 보안 관련 HTTP 헤더가 설정되지 않은 이유는 무엇인가요?

보안 검사 도구는 Mendix가 HTTP 헤더를 설정하는 방식에서 취약점을 보고할 수 있습니다. 이는 일반적으로 Access-Control-Allow-Origin, Content-Security-Policy, Referrer-Policy, X-Content-Type-Options, X-Frame-Options, X-Permitted-Cross-Domain-Policies, X-XSS-Protection 또는 Pragma 헤더, 또는 정보 공개에 대한 일반적인 의견과 관련됩니다.

### 보안 관련 HTTP 헤더 누락 / 헤더의 안전하지 않은 값

*앱 보안 모범 사례 구현 방법*의 [HTTP 헤더 추가](/howto/security/best-practices-security/#adding-http-header) 섹션에 설명된 대로 자체 HTTP 헤더를 추가할 수 있습니다.

### Content Security Policy(CSP) 누락/잘못된 구성

Mendix 9.12.0 이상에서의 Content Security Policy 개선 사항에 대한 정보는 [Content Security Policy](/howto/security/csp/)를 참조하십시오.

### 서버 응답 헤더의 민감한 정보(배너 그래빙)

기본적으로 웹 서버의 HTTP 응답은 웹 서버의 유형과 버전에 대한 정보를 공개합니다. 이 정보는 공격자가 공격을 정교하게 다듬는 데 유용할 수 있습니다. 직접적으로 악용할 수는 없지만, 적에게 가능한 한 적은 정보를 공개하는 것이 보안 모범 사례입니다.

Mendix는 이 접근 방식을 "은폐를 통한 보안(security by obscurity)"으로 간주합니다. 응답에 이 정보를 포함하는 것이 유효한 보안 위험이라고 생각하지 않습니다. 보안 팀과 함께 이 정보를 숨기지 않기로 결정했습니다.

좋은 예로 웹 서버 정보 노출(예: "Server: nginx")이 있습니다. 첫째, 가장 일반적인 웹 서버 유형은 nginx, IIS 및 Apache입니다. 따라서 이 세 가지 웹 서버의 공개적으로 알려진 취약점은 이 정보가 노출되었는지 여부에 관계없이 시도됩니다. 둘째, [Mendix buildpack](https://github.com/mendix/cf-mendix-buildpack)은 공개 GitHub 리포지토리에 있으며, Mendix가 nginx를 웹 서버로 사용하고 있음을 쉽게 확인할 수 있습니다. 응답 헤더에서 이를 숨기더라도 Mendix 앱이 더 안전해지지 않습니다.

### 캐시 제어 헤더가 잘못 설정됨

Mendix 앱은 두 가지 유형의 콘텐츠를 사용합니다: 동적 콘텐츠와 정적 콘텐츠.

동적 콘텐츠는 페이지에 표시되는 데이터로 구성됩니다. 이 데이터는 데이터베이스에서 검색되어 Mendix Runtime에서 제공됩니다.

Mendix Runtime의 모든 요청은 Cache-Control 헤더를 `no-store`로 설정합니다. 이러한 요청에는 민감한 데이터가 포함될 수 있으며, Cache-Control 헤더를 `no-store`로 설정하면 응답이 캐시되는 것을 방지합니다.

정적 콘텐츠의 경우, index.html 및 login.html 파일만 Cache-Control 헤더가 `no-cache`로 설정되어 있습니다.

나머지 정적 콘텐츠의 경우, Cache-Control 헤더가 설정되어 있지 않습니다. 정적 콘텐츠의 가용성과 이 콘텐츠에 대해 캐시 제어 헤더가 관련이 없는 이유에 대한 논의는 아래의 [앱에서 정적 파일이 공개적으로 접근 가능한 이유는 무엇인가요?](#static-content)를 참조하십시오.

Mendix Cloud의 경우, 이 헤더의 설정을 변경할 수 없습니다. Mendix Cloud 외부에서 실행 중인 경우, 자체 인프라 내에서 이를 변경할 수 있을 수도 있습니다.

캐시 제어 지시문에 대한 가능한 값은 *mdn web docs* 사이트의 [Cache Control – Directives](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Cache-Control#directives)를 참조하십시오.

## 앱에서 정적 파일이 공개적으로 접근 가능한 이유는 무엇인가요?{#static-content}

Mendix 앱은 두 가지 유형의 콘텐츠를 사용합니다: 정적 콘텐츠와 동적 콘텐츠. 정적 콘텐츠는 주로 페이지 템플릿(예: `*.xml` 및 `*.xml.gz`), 이미지(예: `*.png`), 아이콘(예: `*.svg`), JavaScript 파일(예: `*.js`) 및 스타일링(예: `*.css`)으로 구성됩니다. 동적 콘텐츠는 페이지에 표시되는 데이터입니다. 이 동적 데이터는 데이터베이스에서 검색됩니다.

기본적으로 앱의 정적 콘텐츠는 공개적으로 사용 가능합니다. 이는 디렉토리 목록을 만들고 웹 서버의 파일에 접근할 수 있음을 의미합니다. Mendix 클라이언트는 이를 기대하며 그렇지 않으면 제대로 작동하지 않습니다. 로그인하지 않고도 정적 콘텐츠를 요청할 수 있습니다. 정적 콘텐츠에는 일반적으로 민감한 데이터가 포함되지 않으므로 문제가 되지 않습니다. 데이터가 표시되고 로직이 적용되는 프레임워크를 제공합니다. 정적 파일에 민감한 데이터를 추가해서는 안 됩니다(예: 페이지의 텍스트 Widget에). Mendix 앱은 민감한 데이터를 저장하기 위한 보다 안전한 방법을 제공합니다.

[접근 제한 프로필 구현](/developerportal/deploy/access-restrictions/)을 통해 전체 앱에 대한 접근을 제한하여 앱의 정적 콘텐츠에 대한 접근을 제한할 수 있습니다. 정적 파일에 대해서만 접근을 제한하는 것은 불가능합니다.

## 이 보고된 보안 발견 사항이 내 앱에 영향을 미치나요?

보안 스캐너로 앱 또는 Mendix 플랫폼을 검사하면 스캐너가 발견한 보안 발견 사항에 대한 보고서가 간혹 생성됩니다. 아래 섹션에서는 이러한 보고서가 Mendix 앱 및 Mendix 플랫폼과 관련하여 무엇을 의미하는지 설명합니다.

### Mendix Cloud에서 지원되는 약한 암호화

Mendix Cloud에서는 보안이 최우선 사항이며, 이를 지속적으로 개선하려고 노력합니다. Mendix Cloud는 TLS 1.3을 지원하며 '충분한' 암호화보다 '양호한' 암호화를 선호하는 암호화를 강제합니다. [Internet.nl](https://www.internet.nl/)과 같은 도구를 사용하여 사이트의 TLS 버전 및 암호화 정보를 보고할 수 있습니다.

### 세션 시간 초과 없음/긴 세션 시간 초과

Mendix의 기본 세션 시간 초과는 10분입니다. 이 시간 초과는 **SessionTimeout** [런타임 설정](/refguide/custom-settings/#general)을 구성하여 변경할 수 있습니다. 기본적으로 Mendix 클라이언트는 활동이 없을 때 세션을 유지하기 위해 keepalive 메시지를 보냅니다. 이는 **EnableKeepAlive** 런타임 설정의 값을 변경하여 변경할 수 있습니다. Mendix Cloud에서는 *환경 상세* 페이지의 *Runtime* 탭에서 사용자 정의 런타임 설정을 설정할 수 있습니다.

### 관리자 계정의 동시 로그인

기본적으로 최종 사용자는 동시에 여러 세션을 가질 수 있습니다. 이를 통해 여러 브라우저에서 동시에 애플리케이션에 로그인할 수 있습니다. 이는 애플리케이션의 프로젝트 설정에서 [사용자당 다중 세션](/refguide/app-settings/#multiple-sessions)을 변경하여 구성할 수 있습니다. 이 설정은 모든 최종 사용자에게 적용됩니다. 관리자 최종 사용자에 대해서만 다중 세션을 비활성화하려면 [사용자 정의 솔루션](https://bartgroot.nl/mendix/custom-checks-on-login/)을 구현해야 합니다.

### Bootstrap 취약점

Mendix는 Bootstrap JavaScript 파일과 함께 제공되지 않습니다. 모든 Bootstrap 스타일링은 Mendix Atlas UI 테마에 포함되어 있습니다.

보안 검사에서 Bootstrap이 플래그 처리되면 사용자 정의 테마에서 Bootstrap 라이브러리를 사용하고 있을 수 있습니다.
따라서 Mendix는 다음 중 하나를 수행할 것을 제안합니다:

* 라이브러리를 직접 업데이트하십시오
* Bootstrap이 필요하지 않도록 사용자 정의 테마를 변경하십시오

### Spring-bean 라이브러리 - Java 역직렬화 - CVE-2016-1000027

Mendix Runtime은 Spring 프레임워크를 사용하지 않습니다. 이 보고서를 받는 이유에 대한 정보는 위의 [일부 Java 라이브러리에서 취약점이 보고되는 이유는 무엇인가요?](#java-libraries) 섹션을 참조하십시오.

예를 들어, [LDAP Synchronization 모듈](https://marketplace.mendix.com/link/component/24)(현재 지원 중단됨)의 이전 버전에는 spring-beans-4.3.9.RELEASE.jar이 있었지만, 2020년 1월에 개발자가 릴리스한 버전에서는 모듈 릴리스 노트에 명시된 대로 해당 종속성을 제거했습니다:

> * 모듈에서 사용하는 모든 Java 라이브러리를 최신 버전으로 업데이트했습니다. Java 컴파일 또는 Runtime 오류가 발생하면 userlib 폴더에서 다음 라이브러리를 삭제해 볼 수 있습니다(적용하려면 새 배포가 필요합니다): 
> 
>     * spring-beans-4.3.9.RELEASE.jar 
>     * spring-core-4.3.9.RELEASE.jar 
>     * spring-ldap-core-2.3.1.RELEASE.jar 
>     * spring-tx-4.3.9.RELEASE.jar 
>     * org.slf4j.slf4j-api-1.7.25.jar 
>     * commons-lang-2.5.jar

### Dojo 라이브러리

{{% alert color="info" %}}
Dojo 라이브러리는 Dojo 클라이언트에서만 사용되며 React 클라이언트에서는 사용되지 않습니다.
{{% /alert %}}

#### deepCopy 취약점 - CVE-2020-5258

Dojo 클라이언트를 사용하는 경우, Mendix 클라이언트는 전체 Dojo 라이브러리와 함께 번들됩니다. 그러나 Dojo 라이브러리의 모든 기능이 사용되는 것은 아닙니다. 취약점은 Dojo의 `deepCopy` 유틸리티 메서드에 있으며, 이 메서드는 Mendix 클라이언트에서 사용되지 않습니다. 이 취약점은 클라이언트에서 악용될 수 없습니다.

#### 프로토타입 오염 취약점 - CVE-2021-23450

Mendix 버전 9.11.0~9.24.0은 Dojo 1.16.4를 사용합니다. `setObject` 함수는 코드의 한 곳에서 사용되지만, 이는 더 이상 사용되지 않는 함수입니다. 이 함수는 더 이상 내부적으로 사용되지 않습니다. 따라서 `setObject` 함수가 악용될 기회가 없습니다.

Mendix 9.24.0 이상은 이 취약점이 없는 Dojo 1.17.3을 사용합니다. 업그레이드하면 보안 도구에서 취약점이 보고되는 것을 방지할 수 있습니다.

### BREACH 공격

Mendix Runtime은 Mendix Runtime이 [BREACH 공격](https://www.breachattack.com/)에 취약하지 않도록 여러 완화 방법을 구현합니다. 이러한 권장 완화 방법은 다음과 같이 리소스를 보호합니다:

* 사용자 입력에서 비밀 분리
* 요청별 비밀 무작위화
* 비밀 마스킹
* CSRF로 취약한 페이지 보호

## 로그 메시지

### ERROR - Connector: 404 - file not found for file

애플리케이션 접근 로그에서 `ERROR - Connector: 404 - file not found for file`이라는 항목이 보이면, 이는 내부 보안 검사 또는 외부 공격에서 비롯될 수 있습니다. 크롤러의 공격을 적극적으로 차단하려고 노력합니다.

추가 조사를 위해 [접근 로그 다운로드](/developerportal/operate/logs/)를 권장합니다. 이를 통해 IP 주소를 검토하고, 위치를 식별하며, 요청이 어디에서 발생하는지 확인할 수 있습니다. 잠재적인 악성 공격이 의심되는 경우, 두 개의 IP 범위를 허용하고 의심되는 IP 주소를 제외하는 [접근 제한 프로필](/developerportal/deploy/access-restrictions/)을 추가하여 보안을 강화할 수 있습니다.
