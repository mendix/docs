## 소개

컴포넌트의 보안은 일반적이고 세분화된 방식으로 설정해야 합니다. 모듈 역할을 선택할 때, 최종 사용자에게 최대한의 유연성을 허용하는 가장 세분화된 구성을 생각하십시오. 

## 모듈 보안

모듈 보안에는 다음 권장 사항이 적용됩니다:

* 사용자가 커스터마이즈할 필요 없이 컴포넌트를 확장할 수 있도록 UI가 제한적이거나 없더라도 항상 모듈 역할을 설정해야 합니다. 
* **Documentation** 필드에서 각 역할의 목적을 명확하게 설명하는 명확하고 세분화된 역할을 사용하십시오.
* 보안을 가능한 한 간단하게 유지하십시오. 세분화와 단순성 사이의 균형을 찾으십시오. 
* 항상 구성과 데이터 액세스를 분리하십시오.  
관리자는 대부분의 조직에서 데이터에 액세스할 수 없어야 합니다. 조직이 다른 경우 항상 모듈 역할을 결합할 수 있지만, 소비자는 분할할 수 없습니다.
* [앱 보안 모범 사례를 구현](/howto/security/best-practices-security/)하십시오.

자세한 내용은 [모듈 보안](/refguide/module-security/)을 참조하십시오.

## Entity 보안

도메인 모델에 액세스 규칙과 읽기 또는 쓰기 권한을 적용하는 방법을 생각하십시오. 예를 들어, 객체에 권한을 부여하지 않으면, 개발자는 데이터 변환 레이어를 사용하고 자체 객체를 만들어 페이지를 빌드하거나, 커넥터에서 오는 결과로 자체 객체를 보강해야 합니다.

## 비밀번호 및 기타 API 키

엔드포인트에 대한 비밀번호 또는 API 키를 저장하는 경우, 항상 [Encryption](/appstore/modules/encryption/) 모듈을 사용하여 암호화하십시오.

## 일반적인 보안 체계

커넥터를 외부 애플리케이션에 빌드할 때 만날 수 있는 여러 보안 체계가 있습니다.

### 클라이언트 자격 증명

클라이언트 자격 증명을 통한 보안은 매우 기본적인 보안 방법입니다. 로그인 이름과 비밀번호를 사용하므로, 통합하려는 서비스로 보낼 때 유일한 보호 수단은 SSL을 통한 암호화된 연결입니다. 이를 사용할 수 없는 경우, 이 유형의 암호화를 절대 사용하지 마십시오. 

### API 토큰

API 토큰은 API를 보호하는 데 도움이 됩니다. 그러나 일반 텍스트로 전송된 API 페이로드는 여전히 가로챌 수 있습니다. 최소한 SSL 연결이 있는 경우에만 API 토큰을 사용하십시오. 

### OAuth

OAuth는 두 가지 유형이 있습니다:

* Authorization Code 플로우 – 사용자가 OAuth 인증을 통해 서비스에 로그인하여 사용자별로 데이터에 대한 액세스를 부여합니다. 
* Client Credentials – 서버 간 통신을 위한 액세스 토큰과 함께 공개 키와 개인 키를 제공합니다. 

OAuth는 API 요청 중에 비밀 키가 교환되지 않으므로 안전한 체계입니다. 비밀 키를 자체 앱에 안전하게 저장하고 HTTPS를 사용하는 한, API 제공자에 대한 자격 증명이 탈취될 수 없습니다.

### SAML

Mendix Marketplace에서 사용할 수 있는 [SAML](/appstore/modules/saml/) 모듈은 지원되는 인증 방법의 대체 또는 확장으로 사용할 수 있습니다.
