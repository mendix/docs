---
name: docs-draft
description: Drafts new documentation content, as one or more new pages from the matching templates in `templates/`, as additions to existing pages, or both. Use when the user asks to create, write, draft, add to, or start new documentation pages, files, or content.
user-invocable: true
---

Draft new content by following these steps:

1. Check whether the user has provided source material for the content. If material is missing, ask for it in a single prompt before continuing:
    * Links, such as Jira tickets, Confluence pages or Figma
    * Pasted content, such as specs, notes, a Slack thread, a transcript, a draft, a README, code or config snippets, or screenshots

    Read each link you have a tool for, and treat pasted or typed content as a source too. Also follow the links inside those sources that belong to the same feature, because the detail is often there. Go one level deep, and skip links about other features. If a source is too broad to read in full, such as a Figma board, a long thread, or a whole space, ask for the part that covers this change, and which parts are final. If you can't access a link, say so in your first message.
2. Check that the sources give the facts the page needs, not only a rationale or roadmap. Leave out anything marked "possible," "to be confirmed," or "out of scope." Ask before planning only if the draft is blocked. Then correlate the sources. When they conflict, don't treat any one as definitive, and note the conflict in the plan. A merged pull request isn't proof that a change shipped, so confirm the change is in the specified release version. If the sources lack the facts the content is built on, or the details aren't final, don't draft yet. Say in the plan what you need to proceed, and let the user decide whether to send it or accept placeholders.
3. Explore `content/en/docs/` and decide whether the content needs new pages, additions to existing pages, or both, and where each belongs (if it isn't clear, ask in the plan). Read the section's `_index.md` and at least two sibling pages closest in topic to match their conventions, and name them in the plan. For additions to an existing page, follow that page's structure.
4. Search the whole `content/en/docs/` tree for the content's main terms. State the terms and folders you searched in the plan. Ignore the versioned folders for older Mendix versions (`refguide10`, `howto9`, and so on) unless the user says the page is for that version. If a page already covers the entire topic, ask in the plan whether to update that page instead. If a page covers part of it, link to that page instead of repeating the covered content, and ask in the plan whether the missing content belongs on that page or on a new one.
5. For each new page or release note entry, read `templates/README.md` to choose the template, then read that template from `templates/` and follow its comments. If only `general-page-template.md` fits a page, say so in the plan and ask whether to base its structure on sibling pages.
6. Present a plan for the user to confirm or adjust. Match it to the size of the change. For a small change to one page, give a few lines: what changes and where, any conflict between sources, and what you need from the user. For new pages or changes across several pages, open with one line saying what you need from the user to proceed, then use these sections, in this order, with the same headings every time:
    1. **Request summary** – The request in one or two sentences, and the target release if there is one, with its source.
    2. **Readiness** – What the sources give, what is missing, and anything that makes the sources less reliable, such as unconfirmed or unfinished content, open design questions, a conflict between sources, or a flag saying documentation isn't required.
    3. **Sources** – What you read, including the links you followed, and the terms and folders you searched.
    4. **Planned changes** – What you will create or change. For several pages, use a table with one row for each page: the page, new or existing, the change size, and what you will add and where. For a single page, list its sections or changes instead. For each new page, add its template, location, file name, sections, and the sibling pages it follows. For each placeholder, say who can fill it. Then state low-stakes choices, such as placement, cross-references, and whether a release note is needed, as defaults the user can overrule.
    5. **Needed from you** – What the user must provide to proceed, grouped by kind, such as screens or labels, release and scope, and permissions or rules. Ask only for what the draft needs, in one prompt and ordered by what blocks it, and never for more than five items. If nothing is needed, say so. Then list the links you couldn't open, with what to export or paste for each.

    Don't fill in missing or ambiguous information. Ask for it, or plan a placeholder for gaps the user can't fill yet. If the sources lack the facts the content is built on, stop after the plan and don't create files until the user replies.
7. Create each new file based on its template. Add the planned content to existing pages in place. For release notes, add the new section to the existing file, using the template's structure, and create the file only if none exists.
8. Clean up each new page as the template's comments and the Content Creation Workflow in CLAUDE.md describe. Complete the required front matter, and keep an optional section only if most of the nearby pages from step 3 have it. If nearby pages have a section that the source material doesn't cover, don't fill it in. Ask the user for the information in a single question, and delete the section if they have none.
9. Complete the introduction and the remaining sections of each new page. Add images only if the user provides them. Where an image is needed and none is available, leave out the `figure` shortcode and list the location in your final summary.
10. Compare the files you created or changed with the input the user provided, and give the user a summary of what you did. Flag any input you left out and why. Search sibling pages and flag anything in other files that the new pages make outdated (such as labels or dates) and any conflicts with the new pages. Note any pages that need a link to the new pages. Prioritize technical accuracy. If it isn't clear which source to trust, ask the user. For release notes, flag changes whose release inclusion couldn't be verified, missing customer impact or compatibility information.
11. Verify that any linked pages exist in the repo. Link to the related pages found in step 3, and link the new pages to each other where relevant.
12. Run the `docs-copyedit` and `docs-alt-text` skills on each new page and on the content you added to existing pages.
13. Run the `docs-pr-review` skill.
