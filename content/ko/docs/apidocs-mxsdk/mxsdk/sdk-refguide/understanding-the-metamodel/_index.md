## 유닛

Mendix Metamodel을 공개했으며, 이는 모든 Mendix 앱 모델이 어떻게 구성되는지에 대한 상세한 설명입니다. 이 문서 세트는 Mendix Metamodel을 이해하는 데 도움을 줍니다.

Studio Pro에 익숙하다면 Mendix 모델이 트리로 구성되어 앱 탐색기를 통해 접근할 수 있는 문서(마이크로플로우(Microflow), 도메인 모델(Domain Model), 페이지, 레이아웃, 모듈, 폴더 등)의 모음이라는 것을 알고 계실 것입니다. SDK에서는 문서를 `units`라는 일반 이름으로 지칭합니다. 기본적으로 Studio Pro의 앱 탐색기에 있는 모든 항목이 `unit`입니다.

유닛은 두 가지 종류로 나뉩니다:

* 구조적 유닛(Structural units) – 앱 트리의 노드이며 전체 앱(루트), 모듈 및 폴더만 될 수 있습니다. 구조적 유닛은 주로 구조를 제공하며 자체적으로는 매우 적은 정보를 포함합니다.
* 모델 유닛(Model units) – 앱 트리의 리프입니다: 마이크로플로우(Microflow), 페이지 등. Studio Pro의 편집기에서 편집할 수 있습니다. 내부적으로 모델 유닛은 *엘리먼트*라고 부르는 모델 객체의 모음입니다.

## 엘리먼트

각 모델 유닛은 엘리먼트의 트리로 구성됩니다. 엘리먼트의 예로는 도메인 모델(Domain Model)의 엔티티(Entity), 엔티티(Entity)의 속성, 마이크로플로우(Microflow)의 액티비티(Activity)와 화살표, 페이지의 위젯(Widget) 등이 있습니다.

각 엘리먼트에는 내부적으로만 사용되는 ID와 `Entity` 또는 `Attribute` 등의 타입이 있습니다. 일반적으로 Studio Pro에서 보이는 것과 엘리먼트 사이에 항상 1:1 대응이 있는 것은 아닙니다. Mendix가 지원하는 다양한 구성을 캡처하기 위해, 그리고 때로는 기술적으로 더 편리하기 때문에 Studio Pro에서 한눈에 볼 수 있는 것보다 더 많은 엘리먼트를 사용해야 하는 경우가 많습니다.

예를 들어: 엔티티(Entity)에는 일반화(Generalization)가 있을 수 있습니다. 일반화가 없으면 Studio Pro에서 **(none)**으로 표시되지만, Entity 엘리먼트에서는 `NoGeneralization` 타입의 엘리먼트로 표현됩니다. 엔티티(Entity)에 일반화가 있으면 일반화 엔티티(Entity)에 대한 참조를 보유하는 `Generalization` 타입의 엘리먼트로 표현됩니다. 참조 문서와 함께 제공되는 이미지가 이러한 구성을 안내합니다.

### 추상 엘리먼트 타입

많은 엘리먼트(또는 엘리먼트 타입)가 기능을 공유합니다. 예를 들어: 마이크로플로우(Microflow)와 규칙은 공통 추상 타입 `MicroflowBase`에 표현된 많은 기능을 공유합니다. 모든 추상 타입은 `Base` 접미사가 붙으며 직접 생성해서는 안 됩니다. 그러나 분석에 유용합니다: 예를 들어 마이크로플로우(Microflow)와 규칙을 대부분 같은 방식으로 처리할 수 있습니다.

## 속성

거의 모든 엘리먼트에는 하나 이상의 속성, 더 정확히는 값이 있습니다. 속성은 엘리먼트의 타입에 의해 결정되며, 속성 값의 타입은 속성에 의해 결정됩니다. 이들은 일반적으로 **Properties** 패널/뷰에서 편집 가능한 값으로 표시됩니다. 이전의 엘리먼트와 마찬가지로 일부 속성은 기술적 성격이며 Studio Pro에 표시되는 것과 1:1로 명확하게 매핑되지 않는 것처럼 보입니다. 예를 들어 엔티티(Entity)의 `Location` 속성은 Studio Pro에서 엔티티(Entity)가 그려지는 위치를 나타냅니다.

### 참조

참조는 특별한 유형의 속성입니다. 참조는 **by id** 또는 **by name**일 수 있습니다. By-id 참조는 *동일한* 모델 유닛의 엘리먼트를 가리키는 데 사용됩니다. By-name 참조는 정규화된 이름으로 *모든* 모델 유닛의 엘리먼트를 가리키는 데 사용됩니다.

## 인터페이스

Model SDK를 사용하여 모델을 열면 전체 모델이 다운로드되지 않습니다: 모델은 매우 클 수 있으며, 일반적으로 모델을 다루기 위해 전체 모델을 "알" 필요가 없습니다—분석조차도 일반적으로 유닛별로 수행할 수 있습니다. 따라서 대역폭과 메모리 소비를 절약하기 위해 처음에는 모든 유닛의 *인터페이스*만 반환합니다. 유닛의 인터페이스는 *공개*로 정의한 유닛의 부분으로 구성되며, 이는 일반적으로 전체 유닛 내용에 비해 매우 작습니다. *다른* 모델 유닛에서 참조할 수 있는 모든 정보(예: 이름)는 공개됩니다.

예를 들어, 도메인 모델(Domain Model)의 경우 다음 항목이 공개이며 따라서 유닛 인터페이스의 일부입니다:

* 모든 엔티티(Entity), (크로스)연관(Association)
* 각 엔티티(Entity)의 이름, 일반화(Generalization) 및 속성
* 각 속성의 이름 및 타입 정보
* 각 (크로스)연관(Association)의 이름

문서, 유효성 검사 규칙 등 기타 모든 세부 사항은 다른 모델 유닛에 관심이 없으므로 유닛 인터페이스에서 사용할 수 없습니다. 이 정보를 사용하면, 예를 들어 메모리에 도메인 모델(Domain Model) 유닛의 인터페이스만으로도 다른 유닛의 마이크로플로우(Microflow) 액티비티(Activity)에서 엔티티(Entity)를 참조할 수 있습니다.

모든 엘리먼트 타입에는 인터페이스와 전체 형태가 모두 있습니다. JavaScriptDoc에서 [Entity 인터페이스](https://apidocs.rnd.mendix.com/modelsdk/latest/interfaces/domainmodels.ientity.html)와 [전체 Entity 클래스](https://apidocs.rnd.mendix.com/modelsdk/latest/classes/domainmodels.entity.html)에서 사용 가능한 정보의 차이를 쉽게 확인할 수 있습니다. 유닛 인터페이스는 공개 엘리먼트의 인터페이스 형태만 포함합니다.

서버가 모든 유닛 인터페이스를 보낸 후, Model SDK 클라이언트는 사용 가능한 정보에서 앱 트리를 재구성합니다. 그러나 (기존) 유닛/엘리먼트를 조작하거나 인터페이스에서 사용할 수 없는 정보에 접근하려면 전체 유닛/엘리먼트를 얻어야 합니다.
