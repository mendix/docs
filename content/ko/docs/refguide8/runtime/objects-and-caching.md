## 소개

이 페이지에서는 데이터베이스에서 객체가 어떻게 로드되는지, 어떤 경우에 객체가 캐시되는지, 캐시된 객체가 언제 검색되는지, 그리고 객체가 변경되고 커밋될 때 어떤 일이 발생하는지 설명합니다.

"객체"라는 용어는 Mendix Entity의 인스턴스를 의미합니다.

## 객체 캐싱

Mendix는 여러 요청에 걸쳐 Mendix Runtime 내에서 객체를 캐시하지 않습니다. 요청 내에서 변경된 객체에 대한 참조를 수집하고 유지합니다. 일부 검색 작업에서는 이 객체가 데이터베이스보다 우선하며, 다른 경우에는 그렇지 않습니다. 이는 성능과 시스템 작동 방식에 영향을 미칩니다.

## 추적되는 객체

Non-Persistable 객체, 새 객체, 변경된 객체만 추적됩니다. 즉, Runtime에서 요청 기간 동안 메모리에 유지됩니다. 요청이 완료되면 객체 상태가 클라이언트에 반환되거나, 비클라이언트 작업의 경우 삭제됩니다. 객체가 커밋되면 Non-Persistable 객체를 제외하고는 더 이상 추적되지 않습니다. 객체 롤백에도 동일하게 적용됩니다.

변경되지 않은 기존 객체는 요청 범위에서 추적되지 않습니다. 변경될 때만 추적됩니다!

{{% alert color="warning" %}}
Mendix Runtime은 클라이언트가 해당 상태에 접근할 충분한 권한이 없는 경우 객체 상태를 클라이언트에 반환할 수 없습니다. 즉, 읽기 접근 권한이 없는 객체를 변경하지만 커밋하지 않는 Microflow를 트리거하면 요청이 끝날 때 변경 사항이 삭제됩니다.
{{% /alert %}}

## 추적 범위

객체는 요청 범위에서 추적됩니다. 요청 범위는 항상 세션 범위보다 작으며 컨텍스트 간에 공유할 수 있습니다. `ISession.createContext()` API를 사용하면 새 컨텍스트와 함께 새 요청 범위가 생성됩니다. 컨텍스트가 복제되면 복제된 컨텍스트와 요청 범위가 공유됩니다. 요청 범위에 대한 변경 사항은 모든 복제된 컨텍스트에 표시됩니다.

## 작업

### 추적된 객체를 반환하는 작업

일부 작업은 먼저 요청 범위에서 객체를 읽습니다. 거기에서 사용할 수 없는 경우 데이터베이스에서 읽습니다. 이러한 작업은 다음과 같습니다:

* 경로/연관에 의한 검색 (`Core.retrieveByPath([..])`)
* ID/ID 목록에 의한 검색 (`Core.retrieveId([..])` 및 `Core.retrieveIdList([..])`)

이는 검색할 객체가 요청 범위에서 추적되고 있는 경우(변경됨, 새 객체 또는 Non-Persistable인 경우) 이러한 작업/API를 호출하면 요청 범위의 객체가 반환된다는 것을 의미합니다.

### 추적된 객체를 반환하지 않는 작업

하나의 작업은 항상 요청 범위를 무시하고 항상 데이터베이스에서 객체를 읽습니다: XPath에 의한 검색(모든 변형).

이는 객체가 변경되어 요청 범위에서 추적되고 있더라도 데이터베이스에서 객체의 새 복사본을 읽는다는 것을 의미합니다. 동일한 Entity 인스턴스의 복사본 중 하나에 대한 변경 사항은 다른 복사본에 표시되지 않습니다!

## 영향

### 솔루션에 대한 이 동작의 영향

Entity 인스턴스에 대한 여러 참조가 있고 이러한 참조를 서로 다른 방법으로 얻은 경우, 동일한 Entity 인스턴스의 복사본일 수 있습니다. 복사본 중 하나에 대한 변경 사항이 다른 복사본에 반영되지 않는다는 점에 유의하십시오.

이를 확인하는 명확한 방법이 없으므로, 최신 버전의 객체를 확보하려면 데이터베이스에 변경 사항을 커밋한 후 즉시 객체를 다시 읽어야 합니다.

### Microflow에 대한 영향

이 동작은 Microflow에도 비슷한 방식으로 영향을 미칩니다. 따라서 여기에서의 모범 사례는 (잠재적으로) 동일한 객체의 다른 참조에 변경 사항을 커밋한 직후 객체를 다시 로드하는 것입니다.

### Microflow와 Java Action에서 Non-Persistable Entity 및 변경된 Entity 사용의 영향

사용자가 클라이언트에서 Microflow를 호출하면 상태의 복사본이 요청과 함께 Runtime으로 전송됩니다. 이 복사본은 Runtime에 유지되며 이 요청을 처리하는 동안 Runtime에 의해 업데이트됩니다. 요청 처리가 완료되면 클라이언트로 반환되며, 클라이언트는 응답에서 반환된 정보로 클라이언트 상태를 업데이트합니다.

서버 측에서는 해당 요청 처리 작업만이 이 상태에 접근할 수 있습니다. 즉, 다른 요청에 의해 업데이트된 Non-Persistable Entity의 상태를 클라이언트를 통하지 않고 쿼리할 수 없습니다(다른 요청이 이 Non-Persistable Entity를 클라이언트에 반환하고, 클라이언트가 후속 요청과 함께 이를 서버에 보내야 합니다).

요청이 Runtime에서 비동기 작업을 트리거하면 시작된 시점의 상태를 가져옵니다. 이 작업이 클라이언트에 의해 비동기적으로 실행된 경우에만 비동기 작업이 완료되었을 때 클라이언트에서 작업을 추적하고 업데이트된 상태를 가져올 수 있습니다. Java Action을 사용하여 Runtime에서 비동기 작업이 트리거된 경우, 상태 업데이트를 클라이언트에서 추적할 수 없습니다(새로 고침, 데이터 유효성 검사 및 기타 지침과 유사).
