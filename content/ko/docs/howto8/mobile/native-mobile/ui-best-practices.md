## 소개

이 문서에서는 Mendix 플랫폼 사용자가 Native Mobile 앱의 사용자 인터페이스(UI)를 구축하는 방법에 대해 설명합니다. 테스트 및 배포와 같은 다른 주제는 여기에서 다루지 않습니다. 이 문서의 가이드라인은 일반적인 조언이며 사용 사례와 특정 상황에 더 잘 맞도록 조정할 수 있습니다.

## 역할

네이티브 애플리케이션을 빌드할 때 앱 개발에 다양한 역할이 필요합니다. 개발자가 여러 역할을 수행할 수 있으므로 모든 역할에 반드시 다른 사람이 있어야 하는 것은 아닙니다. 또한 앱에 따라 특정 역할 간의 전문성 수준에 차이가 있어야 합니다.

### 역할의 다양한 유형

대부분의 앱에서 개발 팀은 전체 구성에 다음 역할을 포함해야 합니다:

* **Mendix 개발** – Domain Model, 페이지, 로직, 통합 및 앱의 전체 흐름을 구축합니다. 이것이 가장 일반적이고 사용 가능한 역할입니다.
* **프론트엔드 개발** – 디자인에서 생성된 앱의 스타일링 또는 테마를 구현합니다.
* **UI 디자인** – 화면과 컴포넌트의 모양 등 사용자 인터페이스를 디자인하고, 테마 색상, 타이포그래피, 간격 및 테두리를 결정합니다.
* **UX 디자인** – 앱의 흐름과 같은 사용자 경험을 디자인하고, 지원할 사용 사례를 결정하며, 특정 기능이 어떻게 작동해야 하는지 결정합니다.
* **Widget 개발 (선택 사항)** – Mendix에서 기본 제공하거나 Mendix Marketplace를 통해 사용할 수 없는 새로운 상호 작용 패턴이나 UI 컴포넌트를 제공하는 새 Widget을 구축합니다.

위에서 언급한 대로 모든 앱에 이러한 역할 각각을 처리하는 다섯 명의 사람이 필요한 것은 아닙니다. 다양한 팀 구성이 일반적입니다.

### 역할, 인력 및 앱 유형

어떤 역할과 인력이 개발 팀을 구성하는지는 제작하는 앱의 유형에 따라 다릅니다. UI나 UX 전문성이 덜 필요한 경우(주로 B2E 앱), Mendix 개발자가 모든 역할을 수행할 수 있습니다. 기본 테마가 충분하거나 시간과 예산에 제약이 있는 경우 이것이 효과적인 구성이 될 수 있습니다. Mendix의 기본 Atlas 테마를 사용하고 사용자 또는 제품 소유자와 논의하면 한 명의 Mendix 개발자가 UI와 UX를 혼자 구축할 수 있습니다.

사용자 정의 UX나 UI가 더 중요한 앱(예: B2C 및 B2B 앱)에서는 다음 조합이 자주 사용됩니다:

* **UI 디자인 + UX 디자인** – 사내 UX 팀을 사용하거나 디자인 에이전시를 고용하는 경우 이 구성이 자주 사용됩니다.
* **UI 디자인 + UX 디자인 + 프론트엔드 개발** – 디자인과 UX를 구현하는 기술도 갖춘 UX 또는 UI 전문가가 이 구성의 핵심입니다. 예를 들어, Mendix Expert Services의 여러 사람이 이러한 유형입니다.
* **Mendix 개발 + 프론트엔드 개발** – 스타일링을 구현하는 방법을 알지만 디자인을 만들 기술은 없는 Mendix 개발자입니다.

## 프로세스

Mendix에서는 개발을 확장하고 속도를 높이기 위해 다른 개발자를 활성화하는 것을 강력히 믿습니다. 일반적으로 UI 또는 UX 디자이너보다 Mendix 개발자가 더 많습니다. 따라서 모바일 앱을 빌드할 때 UI 또는 UX 디자이너가 개발을 가속화하기 위해 Mendix 개발자를 최대한 활성화하는 것이 중요합니다.

Mendix로 빌드하는 것을 장난감 블록으로 빌드하는 것과 비교할 수 있습니다. 사용자에게 결합할 수 있는 일반 블록 세트를 제공하면 무엇이든 만들 수 있습니다. 그러나 새로운 유형의 특정 블록을 계속 구매해야 한다면 빌드가 느리고 방해받을 것입니다.

Mendix Native Mobile 앱의 UI 구축에 대해 알아보려면 아래 섹션을 참조하십시오. 디자인을 쉽게 구현하는 핵심 정보는 아래의 [디자인 속성 구성](#configure-design-props) 섹션을 반드시 확인하십시오.

### UI Kit을 사용하여 앱 디자인 만들기

변형을 포함한 재사용 가능한 컴포넌트 세트를 디자인함으로써 UI 디자이너는 페이지를 디자인하는 데 사용할 수 있는 UI Kit을 만들 수 있습니다. 여기에는 브랜드 색상, 타이포그래피, 간격 설정 및 변형을 포함한 UI 컴포넌트(예: 버튼 및 입력)와 같은 설정이 포함됩니다. 디자이너는 이러한 작업을 만족스러운 결과로 완료하기 위해 [Sketch](https://www.sketch.com/) 도구를 자주 사용합니다.

이 UI Kit은 Mendix 테마와 관련 컴포넌트를 만드는 입력이 됩니다. 따라서 Mendix에서 이미 사용 가능한 것과 디자인에 필요한 것을 맞추기 위해 Mendix 및 프론트엔드 지식을 갖추는 것이 도움이 됩니다.

### UI Kit을 Mendix 테마 및 컴포넌트로 변환

프론트엔드 개발자는 UI Kit을 Mendix 테마와 표준 레이아웃으로 변환하고, 빌딩 블록과 페이지 템플릿을 구축할 수 있습니다.

#### 메인 테마 설정 구성

테마 설정을 구성하는 목표는 앱 또는 회사 브랜딩의 룩앤필을 빠르게 구현하는 것입니다. Mendix는 앱의 전체적인 룩앤필을 만드는 데 큰 도움이 되는 고도로 구성 가능한 테마를 제공합니다. 앱의 *theme/styles/native/app/custom-variables.js* 파일에서 테마 설정을 구성하십시오.

#### 디자인 속성 구성 {#configure-design-props}

디자인 속성의 목표는 사용자 정의 클래스 이름을 알거나 사용자 정의 스타일링을 작성하지 않고도 개발자가 디자인을 구현할 수 있도록 하는 것입니다. 이것은 개발자를 활성화하는 매우 중요한 단계입니다.

기본적으로 Mendix에는 개발자가 여러 옵션으로 페이지를 구축할 수 있게 하는 기본 디자인 속성 세트가 있습니다. UI Kit의 변형에 따라 디자인 속성을 변경, 추가 또는 제거하는 것을 권장합니다.

예를 들어, Mendix는 버튼 변형 세트(default, secondary, warning, success, danger)를 제공합니다. 그러나 디자인 과정에서 default와 secondary 변형만 사용하도록 선택할 수 있습니다. 이러한 선택은 UI 디자인의 일부입니다. Mendix 개발자에게 얼마나 많은 자유를 줄지 결정하는 것은 UI 및 프론트엔드 디자인 역할을 맡은 사람들의 몫입니다.

디자인 속성은 *theme/settings-native.json*에 있으며, 자세한 정보는 [Design Properties API 문서](/apidocs-mxsdk/apidocs/design-properties/)에서 찾을 수 있습니다.

#### 앱 레이아웃 만들기

기본 Atlas 테마에는 레이아웃 세트가 미리 번들되어 있습니다. 앱의 디자인에 맞지 않는 경우 레이아웃을 만들거나 사용자 정의하고 적절한 이름을 지정할 수 있습니다. 제공된 레이아웃을 변경하지 마십시오. 사용자 정의 레이아웃, 페이지 템플릿 및 빌딩 블록이 있는 별도의 모듈을 만들거나 자체 [UI 리소스 모듈](/howto8/front-end/create-company-atlas-ui-resources/#moving-from-local-to-atlas-ui-resources)을 만드십시오.

#### 공통 UI 구조를 위한 빌딩 블록 만들기

앱에는 페이지의 패턴 인스턴스가 여러 개 있거나 더 복잡한 UI 패턴이 있는 경우가 많습니다. 이러한 경우 다른 Mendix 개발자가 공통 패턴을 쉽게 적용할 수 있도록 빌딩 블록을 만드는 것이 유용합니다. 빌딩 블록에서는 사용자 정의 클래스 이름을 사용하여 더 구체적으로 만들 수 있습니다. 개발자가 빌딩 블록에서 변경할 수 있어야 하는 속성에 대해서는 가능한 한 디자인 속성을 많이 사용하십시오.

#### 공통 페이지 구조를 위한 페이지 템플릿 만들기

빌딩 블록과 유사하게, 개발자는 다른 개발자가 일반적인 유형의 페이지를 쉽게 구현할 수 있도록 표준 페이지 템플릿을 만들 수 있습니다.

### 테마와 콘텐츠를 사용하여 UI 구현

Mendix 개발자는 앱의 테마, 디자인 속성, 레이아웃, 빌딩 블록 및 페이지 템플릿을 기반으로 앱의 인터페이스를 구축할 수 있습니다. 누락된 기능으로 인해 설계대로 페이지를 구축하기 어려운 경우 UI Kit, 테마 또는 사용 가능한 콘텐츠를 반복하는 것이 좋습니다. 특정 경우에는 다음 섹션에서 설명하는 대로 특정 스타일링을 적용하는 것이 좋을 수 있습니다.

### 앱 또는 사용 사례별 스타일링 구현

앱의 표준 테마와 콘텐츠가 모든 페이지를 구축하기에 충분하지 않은 경우가 여러 가지 있습니다. 이러한 경우 프론트엔드 개발을 사용하여 특정 스타일링을 구현할 수 있습니다. 

### 반복 및 토론

Mendix는 [애자일 개발](https://www.mendix.com/blog/design-thinking-vs-agile-combine-problem-finding-problem-solving-better-outcomes/) 환경을 위한 플랫폼이며, UI Kit 및 관련 Mendix 테마와 컴포넌트를 만들 때도 마찬가지입니다. 계속 반복하고 토론하며 개선하십시오.

## 모범 사례 

### 가능한 한 디자인 속성을 자주 사용하십시오

사용자 정의 스타일링을 피하십시오. 대신 가능한 한 사용 가능한 디자인 속성을 많이 사용하십시오. 이렇게 하면 다른 개발자가 스타일이 적용된 내용을 더 쉽게 이해할 수 있습니다. 패딩과 폰트 크기 스타일을 결합한 속성과 같이 다양한 스타일을 결합하는 단일 디자인 속성을 만드는 것은 권장하지 않습니다.

### 가능한 한 많이 재사용할 계획을 세우십시오

일반적인 함정은 재사용에 대해 생각하지 않고 디자인에서 직접 구현을 시작하는 것입니다. 직접 구현은 소규모 앱에는 의미가 있을 수 있지만, 이 방법은 여러 사용자 정의 클래스를 만들고, 개발을 느리게 하는 컴포넌트의 변형을 더 많이 생성하며, 상당한 기술 부채를 만들 위험이 있습니다.

매우 구체적인 클래스 이름은 피하십시오. 매우 구체적인 클래스 이름은 종종 한 번만 사용되지만 스타일은 최소 몇 번은 사용됩니다. 가능한 경우 클래스를 결합하고 다시 작성하십시오. 이렇게 하면 테마가 깔끔하고 단순하게 유지되며, 디자인 속성을 만들고 Mendix 개발자를 활성화하기가 더 쉬워집니다.

### Core 폴더에서 절대 변경하지 마십시오

**core** 폴더의 스타일링을 변경하면 다음에 Atlas를 업데이트할 때 오류가 발생할 위험이 있습니다. Atlas를 업데이트하는 것도 더 어려울 수 있습니다. 

앱의 전체 스타일링의 상당 부분은 `theme/styles/native/app/custom-variables.js`에서 변경할 수 있습니다. 그러나 더 많은 변경이 필요한 경우 Widget의 기본 스타일링을 확장하거나 기본 스타일링을 직접 정의할 수 있습니다.

### 포함 속성보다 디자인 속성을 선호하십시오

디자인 속성으로 설정할 수 있는 속성을 포함하는 것은 피하십시오. 속성을 신중하게 사용하면 앱이 다른 개발자가 이해하고 변경하기 더 쉬워집니다. 예를 들어, 특정 요소에 항상 마진을 적용하면 특정 디자인에 맞지 않을 가능성이 있습니다. 그러나 개발자는 디자인 속성을 사용하여 쉽게 마진을 설정할 수 있습니다. 특히 유용한 접근 방식은 90%의 경우를 커버하는 기본 간격을 제공하고 개발자에게 디자인 속성을 사용하여 덮어쓸 수 있는 옵션을 제공하는 것입니다. 

### Core 스타일링 연구 

기본 Mendix 테마는 스타일링에 접근하는 방법에 대한 좋은 예제 소스 역할을 하는 완전한 테마입니다.

### 스타일링 유지보수 가능하게 유지하기

단일 파일에 계속 클래스를 추가하는 것은 일반적인 함정입니다. 그러나 이렇게 하면 파일의 유지 관리가 더 어려워집니다. 스타일링을 유지 관리 가능하게 유지하기 위한 몇 가지 모범 사례는 다음과 같습니다:

* 스타일링에 명확하고 설명적이며 일관된 이름을 적용하십시오—필요한 경우 주석을 추가하십시오
* 일관성과 쉬운 업데이트를 위해 가능한 한 많이 변수를 사용하십시오
* 스프레드 연산자 `…`를 사용하여 클래스의 일부를 결합하고 재사용하십시오
* 스타일링을 논리적 부분으로 분할하고 관련 스타일을 함께 그룹화하며, 해당 그룹이 너무 커지면 별도의 파일로 분할하십시오—사용자 정의 스타일링 파일이 여러 개인 경우 *theme/styles/native/app/custom.js*를 사용하여 모든 파일을 가져오십시오(이렇게 하면 사용자 정의가 *app* 폴더에만 있으므로 업데이트가 더 쉬워집니다)
* *Custom.js*에는 클래스가 포함되어서는 안 됩니다—다른 파일의 클래스를 포함하기 위한 `export * from …*` 문만 포함되어야 합니다
* 빌딩 블록 및 페이지 템플릿의 스타일링은 *theme/styles/native/ui_resources/{YOUR_APP_OR_MODULE_NAME}*에 넣고 *theme/styles/native/main.js*에 포함하십시오
* 일반 회사 스타일링과 앱별 스타일링을 위해 app 폴더에 별도의 폴더를 만드십시오(이렇게 하면 앱 간 재사용과 일관성이 가능해집니다)
* 항상 재사용에 대해 생각하십시오; 방금 만든 일반적인 클래스가 다른 앱에서도 유용할 수 있습니다. 회사 테마에 추가하는 것을 고려하십시오
