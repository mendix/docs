## 소개

네이티브 모바일 앱은 웹 애플리케이션과 유사한 방식으로 모델링하지만, 네이티브 모바일 앱에서의 내비게이션은 웹 애플리케이션과 다른 측면이 있습니다. 이 가이드는 이러한 내비게이션 차이점을 설명합니다.

### 웹 앱

일반적으로 웹 앱에서는 주어진 시간에 하나의 페이지만 열려 있습니다. 이는 페이지를 열면 이전 페이지가 새 페이지로 대체되기 때문입니다. 뒤로 이동하면 시작한 페이지가 현재 페이지를 대체하기 위해 다시 로드됩니다. 이 페이지 로딩 패턴은 성능을 저하시킵니다.

### 네이티브 모바일 앱

네이티브 모바일 앱에서는 기본적으로 페이지가 열린 상태로 유지됩니다. 이를 통해 스크롤 위치 및 활성 탭 정보와 같은 이전 페이지의 상태를 유지하면서 즉시 뒤로 이동할 수 있습니다(예: 뒤로 버튼을 탭하거나 스와이프). 이것은 앱의 사용자 경험에 큰 도움이 됩니다. 그러나 Mendix는 모바일 앱을 개발할 때 열린 페이지를 고려할 것을 권장합니다. 특히, 한 번에 너무 많은 페이지가 열리지 않도록(성능 저하를 초래할 수 있음) 하고, 필요할 때 데이터가 새로 고쳐지거나 업데이트되도록 하십시오. 이를 위해 Mendix는 정확한 내비게이션 흐름에 대한 세부적인 제어를 제공합니다.

## 레이아웃 유형

### 기본(Default)

기본 레이아웃이 있는 페이지를 연 후, 헤더의 뒤로 버튼, 디바이스의 뒤로 버튼(Android의 경우) 또는 화면 왼쪽에서 스와이프(iOS의 경우)를 사용하여 이전 페이지로 이동할 수 있습니다. 앱의 홈 페이지가 열려 있을 때 Android 뒤로 버튼을 누르면 앱이 닫힙니다.

### 팝업(Pop-Up)

팝업 레이아웃이 있는 페이지는 기본 페이지처럼 보이지만, 독특한 애니메이션으로 나타나며 뒤로 아이콘 대신 닫기 아이콘이 있습니다. iOS에서는 팝업 상단에서 아래로 스와이프하여 닫을 수도 있습니다. Android에서는 디바이스의 뒤로 버튼을 사용하여 닫을 수 있습니다. 팝업에는 하단 바가 있을 수 없습니다. 팝업 레이아웃이 있는 페이지는 기본 홈 페이지로 사용하거나 하단 바에 추가할 수 없습니다.

팝업은 특정 컨텍스트에서 입력을 요청할 때 매우 유용할 수 있습니다. 예를 들어, QR 코드를 스캔해야 할 때 잘 작동합니다. 또한 마법사(여러 단계가 있는 양식)를 쉽게 만들 수 있으며, 프로세스가 완료되고 모든 팝업이 닫힐 때까지 이전 단계로 돌아가서 변경할 수 있습니다.

## 내비게이션 관련 레이아웃 구성 요소

네이티브 레이아웃에는 네이티브 앱에서 가장 일반적인 패턴을 가능하게 하는 유용한 속성이 있습니다.

### 헤더

헤더 속성이 활성화된 레이아웃은 항상 화면 상단에 바를 표시합니다. 헤더는 세 부분으로 구성됩니다:

* 왼쪽 부분: 구성할 수 없지만 레이아웃 유형에 따라 뒤로 아이콘 또는 닫기 아이콘을 표시할 수 있습니다
* 중앙 부분: 페이지의 제목을 표시합니다
* 오른쪽 부분: 위젯으로 구성할 수 있으며, 주로 버튼을 포함하는 데 사용됩니다

다음은 iOS에서의 기본 헤더 예시입니다:

### 하단 바

네이티브 Navigation Profile에 하단 바 항목을 추가할 수 있습니다. 이 항목은 하단 바 속성이 활성화된 레이아웃이 있는 모든 페이지에 표시됩니다.

하단 바의 각 항목에는 자체 내비게이션 스택이 있습니다. 이는 첫 번째 탭에서 몇 개의 페이지를 열고, 두 번째 탭으로 전환한 후 다시 첫 번째 탭으로 돌아가면 첫 번째 탭의 페이지가 그대로 열려 있음을 의미합니다.

{{% alert color="warning" %}}
하단 바가 없는 페이지는 별도의 스택에서 생성됩니다. 하단 바가 *없는* 페이지에서 하단 바가 *있는* 페이지로 이동하면 해당 스택의 모든 페이지가 닫힙니다.
{{% /alert %}}

## Mendix 네이티브 내비게이션은 어떻게 작동하나요?

기본적으로 페이지는 더 나은 사용자 경험을 제공하기 위해 열린 상태로 유지되지만, 앱의 우수한 성능과 논리적인 흐름을 위해 올바르게 관리해야 합니다.

### 스택

페이지를 열린 상태로 유지하기 위해 내비게이션 시스템은 여러 개의 페이지 스택을 사용합니다. 모바일 앱에는 동시에 여러 스택이 포함될 수 있습니다. 스택은 카드 더미에 비유할 수 있습니다: 상단에 카드를 추가하고 상단에서 카드를 제거할 수 있습니다.

#### 단일 스택

앱이 하단 바를 사용하지 않으면 단일 스택이 있습니다. 이 상황은 웹에서의 내비게이션과 가장 유사합니다. 그러나 스택의 모든 페이지는 명시적으로 닫거나 뒤로 버튼을 누를 때까지 열린 상태로 유지된다는 것을 염두에 두는 것이 중요합니다.

스택의 첫 번째 페이지는 항상 홈 페이지입니다. 페이지를 여는 버튼을 탭하면 스택에 두 개의 페이지가 있게 되며, 이런 식으로 계속됩니다.

페이지를 닫으면(뒤로 버튼, 닫기 액션 또는 뒤로 스와이프(iOS)를 통해) 현재 페이지만 닫히고 이전 페이지가 다시 보이게 됩니다.

{{< figure src="/attachments/refguide8/mobile/native-mobile/native-navigation/singlestack.gif"   width="250"  class="no-border" >}}

#### 다중 스택

앱에 하단 바 항목이 있으면 하단 바의 각 항목에 별도의 스택이 있습니다. 스택 내에서 페이지를 열고 닫아 이동할 수 있습니다.

하단 바 항목이 포커스되어 있지 않으면 누르면 해당 항목이 포커스됩니다. 다른 하단 바 항목으로 전환해도 포커스된 항목의 페이지가 닫히지 않습니다. 항목이 이미 포커스되어 있으면 다시 누르면 해당 스택의 모든 페이지가 해제됩니다.

{{< figure src="/attachments/refguide8/mobile/native-mobile/native-navigation/multiplestacks.gif"   width="250"  class="no-border" >}}

#### 팝업

팝업 레이아웃이 있는 페이지가 열리면 새 스택이 생성되고 이 스택의 모든 페이지가 화면을 완전히 덮습니다. 이전 스택으로 돌아가려면 팝업을 닫아야 합니다.

팝업 내부에서 다른 팝업 페이지를 열 수 있으며, 이 모든 페이지는 단일 스택으로 동작합니다. 팝업에서 일반 페이지를 열면 팝업이 먼저 닫힙니다.

{{< figure src="/attachments/refguide8/mobile/native-mobile/native-navigation/popups.gif"   width="250"  class="no-border" >}}

### 페이지 열기 및 닫기

종종 뒤로 이동할 때 어떤 페이지가 표시되는지를 결정하기 위해 페이지 기록을 제어해야 합니다. 기본적으로 Close page 액션은 현재 스택에서 단일 페이지만 닫지만, 더 많은 페이지를 닫도록 구성할 수 있습니다.

#### 여러 페이지 닫기

Close page 액션에서 적절한 페이지 수를 설정하여 기록의 여러 페이지를 한 번에 뒤로 이동할 수 있습니다. 여러 페이지를 닫는 Close page 액션은 단일 애니메이션으로 나타납니다.

이 동작은 페이지에 모델링한 Close page 액션이나 Nanoflow의 Close page Activity에서 구성할 수 있습니다. 이 숫자는 표현식을 사용하여 설정할 수 있으므로 정적 숫자 또는 더 복잡한 경우를 위한 스냅샷 계산 값을 설정할 수 있습니다.

#### 닫기와 열기 결합

더 복잡한 시나리오의 경우, 새 페이지로 이동할 때 현재 스택의 기록에서 하나 이상의 페이지를 투명하게 제거할 수 있습니다. 이렇게 하면 사용자가 더 이상 관련 없는 페이지로 실수로 돌아가는 것을 방지할 수 있습니다. 예를 들어, 사용자가 3단계 마법사 흐름의 끝에 도달하면 Open page Activity를 구성하여 세 번째 페이지를 열고 동시에 이전 두 페이지를 닫을 수 있습니다. 결과적으로 사용자는 단일 전환을 보게 되며, 뒤로 이동해도 처음 두 페이지로 이동하지 않습니다.

또한 페이지로 이동할 때 Open page 액션에서 **Clear history**를 구성할 수 있습니다. 이렇게 하면 전체 내비게이션 시스템이 효과적으로 재설정되고 사용자는 대상 페이지에서 뒤로 이동할 수 없습니다.

### 데이터 업데이트

데이터에 대한 변경 사항은 모든 활성 화면에 즉시 반영된다는 점을 기억하는 것이 중요합니다. 그러나 이것이 이러한 변경 사항이 데이터베이스에도 커밋된다는 것을 의미하지는 않습니다; 그것은 여전히 명시적인 작업입니다. 이것의 또 다른 결과는 사용자가 변경 사항을 저장하지 않고 뒤로 이동하기로 결정할 때(예: 뒤로 버튼을 누르기) 앱이 데이터 변경 사항을 추적하고 가능하면 되돌릴 책임이 있다는 것입니다.

## 모범 사례 및 패턴

### 사용자를 위해 간단하게 만들기

사용자가 항상 앱에서 자신의 위치와 다음 옵션이 무엇인지 이해하는 것이 중요합니다. 전반적으로 사용자가 자신의 위치와 이동할 수 있는 위치를 볼 수 있도록 하단 바를 표시하는 것이 유용합니다. 그러나 일부 흐름에서는 하단 바가 없는 레이아웃이나 팝업 레이아웃을 사용하여 집중을 만들고 방해 요소를 제거하는 것이 합리적입니다.

### 열린 페이지를 최소화하여 성능 향상

사용자가 앱을 탐색하는 동안 모든 페이지는 백그라운드에서 열린 상태로 유지됩니다. 이것은 디바이스의 리소스를 사용하며, 너무 많은 열린 페이지는 성능 문제를 일으킬 수 있습니다. 이것의 결과로 Open page 또는 Close page 액션 사용 간의 선택은 웹 애플리케이션보다 더 신중하게 이루어져야 합니다.

가능한 경우 Close page 액션(또는 위에서 언급한 Show page 액션의 변형)을 최대한 자주 사용하여 불필요한 페이지가 너무 많이 열려 있지 않도록 하십시오.

### 모달 상호작용에 팝업 사용

대부분의 애플리케이션은 일련의 기본 사용자 흐름으로 구성되며, 각 기본 흐름에는 추가 사용자 입력을 요청하는 것과 같은 보조 흐름이 있을 수 있습니다. 캘린더 앱의 경우, 예정된 이벤트를 탐색하는 것이 기본 흐름이고 하나의 이벤트를 편집하는 것이 보조 흐름일 수 있습니다. 일반적으로 보조 흐름은 기본 흐름을 중단해서는 안 되며, 사용자가 이 보조 흐름을 완료한 후 기본 흐름에서 있던 위치에 도달해야 합니다.

이러한 동작은 여러 페이지를 닫는 기능을 사용하여 모델링할 수 있지만, Mendix는 이러한 시나리오에 팝업 페이지를 사용할 것을 권장합니다. 팝업 페이지는 내비게이션 스택 외부에 완전히 존재하며, 앱의 내비게이션 기록을 중단하지 않고 열고 닫을 수 있습니다.

### 시작 흐름

Open page 액션의 **Clear history** 옵션은 복잡한 동작을 모델링하는 데 사용할 수 있지만, 가장 일반적인 사용 사례 중 하나는 시작 흐름입니다. 시작 시 일련의 튜토리얼 화면을 표시해야 하는 앱을 상상해 보십시오. 이 화면 후에 사용자는 메인 페이지에 도착해야 합니다. 여기서 뒤로 이동할 수 없어야 합니다. 이는 **Clear history** 옵션이 있는 Open page 액션을 사용하여 최종 튜토리얼 화면에서 메인 페이지로 이동함으로써 달성할 수 있습니다.

## 커스터마이징

기본적으로 하단 바와 상단 바에는 기본 스타일링이 있습니다. 이 스타일링을 변경하려면 *네이티브 스타일링 참조 가이드*의 [페이지](/refguide8/native-styling-refguide/#pages) 섹션을 참조하십시오. 그러나 디자인에 맞게 스타일링을 추가로 커스터마이징하려면 Pluggable Widget을 만들어 일부 기본 내비게이션 구성 요소를 대체할 수 있습니다. 자세한 내용은 [Pluggable Widgets API 문서](/apidocs-mxsdk/apidocs/pluggable-widgets/)를 참조하십시오.
