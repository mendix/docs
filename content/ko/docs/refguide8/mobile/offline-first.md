## 소개

오프라인 우선(Offline-first) 애플리케이션은 연속적인 사용자 경험을 제공하기 위해 연결 상태와 관계없이 작동합니다. 페이지와 로직은 디바이스 자체의 오프라인 데이터베이스와 상호 작용하며, 데이터는 서버와 동기화됩니다. 이를 통해 더 빠른 UI, 향상된 안정성, 개선된 디바이스 배터리 수명을 얻을 수 있습니다.

{{% alert color="info" %}}
오프라인 우선은 디바이스의 네트워크 상태에 기반한 접근 방식이 아니라 아키텍처 개념이라는 점을 이해하는 것이 중요합니다. 오프라인 우선 앱은 연결에 의존하지 않지만 연결을 사용할 수 있습니다(예: Microflow 호출, Google Maps 위젯 사용, 푸시 알림 사용).
{{% /alert %}}

Mendix는 [네이티브 모바일](/refguide8/native-mobile/) 및 [하이브리드 모바일](/refguide8/hybrid-mobile/) 앱을 위한 오프라인 우선 애플리케이션 구축을 지원합니다. 네이티브 앱과 하이브리드 앱은 동일한 코어를 공유하므로 동일한 오프라인 우선 기능을 제공합니다. 네이티브 모바일 앱은 항상 오프라인 우선이지만, 하이브리드 모바일 앱의 경우 구성된 네비게이션 프로필에 따라 다릅니다. 데이터는 디바이스의 로컬 데이터베이스에 저장되고, 파일은 디바이스의 파일 저장소에 저장됩니다.

Mendix Studio Pro는 앱이 오프라인 우선 접근 방식을 따르고 연결이 없어도 작동하는지 확인하기 위해 유효성 검사를 수행합니다.

개발 중에는 [Make It Native 8 앱](/refguide8/getting-the-make-it-native-app/)(네이티브 모바일 앱용) 또는 [Mendix Developer App](/refguide8/getting-the-mendix-app/)(하이브리드 모바일 앱용)을 사용하여 디바이스에서 Mendix 앱을 미리보기하고 테스트할 수 있습니다. Mendix 앱이 처음 로드될 때 서버에 세션을 생성하고 필요한 데이터와 리소스를 다운로드하기 위해 인터넷 연결이 필요합니다. 이 초기 동기화 후에는 인터넷 연결 없이도 앱에서 데이터를 사용할 수 있습니다. 이후 동기화는 사용자 요청, 애플리케이션 로직 또는 모델 변경 후에 수행됩니다.

## 동기화{#synchronization}

Mendix는 오프라인 네비게이션 프로필 내에서 사용되는 페이지와 Nanoflow를 기반으로 어떤 Entity를 동기화해야 하는지 자동으로 앱의 데이터 모델을 분석합니다. 또한 플랫폼은 Entity 접근 권한을 고려하여 사용자가 접근 가능한 데이터만 동기화합니다.

동기화는 다음 시나리오에서 자동으로 트리거됩니다:

* 모바일 앱의 초기 시작 시
* 다음 조건이 충족될 때 Mendix 앱이 재배포된 후 모바일 앱의 첫 시작 시:
* 네트워크 연결이 있는 경우
* 새로운 Mendix 버전을 사용 중이거나 오프라인 우선 앱에서 사용하는 Domain Model이 변경된 경우
* 앱 사용자가 로그인 또는 로그아웃한 후

동기화는 Mendix 앱의 다양한 위치에서도 구성할 수 있습니다. 예를 들면:

* 버튼의 액션으로
* Nanoflow의 액션으로
* 리스트 뷰의 풀다운 액션으로 (네이티브 모바일 전용)

동기화는 데이터베이스 수준에서 수행됩니다. 즉, 객체에 대해 커밋되지 않은 변경 사항이 있는 상태에서 동기화하면 로컬 데이터베이스의 Attribute 값이 동기화되며, 커밋되지 않은 변경 사항은 무시됩니다. 커밋되지 않은 변경 사항은 동기화 후에도 계속 사용할 수 있습니다.

### 동기화 유형

두 가지 수준에서 동기화를 수행할 수 있습니다:

* [전체 동기화](#full-sync)
* [선택적 동기화](#selective-sync)

#### 전체 동기화 {#full-sync}

이 모드는 오프라인 우선 앱에서 사용되는 모든 Entity에 대해 업로드 및 다운로드 단계를 모두 수행합니다. [사용자 정의 동기화](#customizable-synchronization)를 사용하여 각 Entity의 동작을 커스터마이즈할 수 있습니다.

#### 선택적 동기화 {#selective-sync}

이 모드를 사용하면 동기화할 특정 객체를 선택할 수 있습니다.

선택적 동기화는 Nanoflow 내의 **Synchronize** 액션을 통해서만 수행할 수 있습니다. UI 요소(예: 버튼, onchange 액션 또는 기타 요소)를 사용하여 수행되는 동기화는 전체 동기화를 수행합니다.

### 동기화 단계

동기화 프로세스는 두 단계로 구성됩니다. [업로드 단계](#upload)에서 앱은 커밋된 새 객체 또는 변경된 객체로 서버 데이터베이스를 업데이트합니다. [다운로드 단계](#download)에서 앱은 서버 데이터베이스의 데이터를 사용하여 로컬 데이터베이스를 업데이트합니다. 동기화는 데이터베이스 수준에서만 작동합니다. 즉, 커밋되지 않은 새 객체와 Attribute 변경 사항은 동기화되지 않습니다.

#### 업로드 단계 {#upload}

업로드 단계는 다음 작업을 실행합니다:

1. 로컬 데이터베이스는 객체를 커밋하거나 삭제해야만 수정할 수 있으므로, 해당 객체는 오프라인 중에 생성된 새 객체이거나 서버에서 이전에 동기화된 기존 객체일 수 있습니다. 업로드 단계는 마지막 동기화 이후 로컬 데이터베이스에 커밋된 객체를 감지합니다. 감지 로직은 동기화 유형에 따라 다릅니다. **Synchronize all**의 경우 로컬 데이터베이스의 모든 커밋된 객체가 검사됩니다. **Synchronize objects**의 경우 선택된 객체 목록에서 커밋된 모든 객체가 검사됩니다.
2. <a id="steptwo"></a>변경되거나 새로운 파일 객체가 있는 경우 해당 콘텐츠가 서버에 업로드되어 임시로 저장됩니다. 각 파일은 별도의 네트워크 요청으로 업로드됩니다. 파일 업로드가 실패하면 서버나 디바이스 데이터베이스에 변경 사항을 일으키지 않고 전체 동기화가 중단됩니다.
3. <a id="stepthree"></a>변경되거나 새로운 모든 객체가 서버로 전송되고, 파일의 콘텐츠가 객체에 연결됩니다. 서버는 객체의 참조 무결성 유효성 검사를 수행합니다(자세한 내용은 아래의 [댕글링 참조](#dangling-references) 섹션을 참조하세요). 객체는 서버 데이터베이스에 커밋됩니다. 이 단계는 단일 네트워크 요청으로 수행됩니다.
4. 이러한 객체에 구성된 커밋 전/후 또는 삭제 전/후 이벤트 핸들러는 평소처럼 서버에서 실행됩니다: 데이터가 업로드된 후, 디바이스 데이터베이스가 업데이트되기 전에 실행됩니다.
    이는 이벤트 핸들러에서 동기화된 객체에 대해 수행하는 추가 변경 사항이 다운로드 단계에서 디바이스 데이터베이스에 적용된다는 것을 의미합니다. 이 규칙에는 한 가지 예외가 있습니다: 이벤트 핸들러에서 파일 Entity의 콘텐츠를 변경하려고 시도하면 변경 사항이 적용되지 않습니다.
    새 객체에 대한 커밋 전/후 이벤트 핸들러도 실행됩니다.

#### 다운로드 단계 {#download}

업로드 단계가 성공하면 서버 데이터베이스의 최신 데이터로 로컬 데이터베이스가 업데이트되는 다운로드 단계가 시작됩니다. 다운로드 단계의 동작은 동기화 유형에 따라 다릅니다.

**전체 동기화** — 서버 데이터베이스에서 최신 데이터를 검색하기 위해 Entity당 서버에 네트워크 요청이 전송됩니다. 앱의 동기화 동작을 사용자 정의하여 로컬 데이터베이스에 동기화되는 Entity를 관리할 수 있습니다. 이 절차에 대한 자세한 내용은 아래의 [사용자 정의 동기화](#customizable-synchronization) 섹션을 참조하세요. 다운로드 프로세스는 파일 Entity의 콘텐츠도 다운로드하여 디바이스 저장소에 저장합니다. 이 프로세스는 증분적입니다. 앱은 파일이 이전에 다운로드된 적이 없거나 마지막 다운로드 이후 변경된 경우에만 파일 객체의 콘텐츠를 다운로드합니다. 파일 Entity의 변경 날짜 Attribute를 사용하여 파일 객체의 콘텐츠가 변경되었는지 확인합니다.

**선택적 동기화** — 동기화를 위해 선택된 객체만 로컬 데이터베이스에 동기화됩니다. 이러한 객체를 검색하기 위한 추가 네트워크 요청은 없습니다. 객체는 업로드 단계에서 수행된 네트워크 요청의 응답으로 반환됩니다. 파일 Entity가 동기화를 위해 선택된 경우, 해당 콘텐츠도 디바이스 저장소에서 증분적으로 업데이트됩니다. 로직은 전체 동기화와 동일합니다.

### 동기화 후

동기화가 완료되면 앱의 현재 페이지에 있는 위젯이 최신 데이터를 반영하도록 새로고침됩니다. 동기화가 Nanoflow에서 트리거된 경우, 모든 Nanoflow 객체/목록 변수가 업데이트됩니다(커밋되지 않은 변경 사항은 그대로 유지됩니다).

동기화 중 객체가 디바이스에서 제거되면 Nanoflow 객체 변수의 값이 동기화 후 `empty`가 될 수 있습니다. 이는 다음과 같은 경우에 발생할 수 있습니다:

* 서버에서 객체가 삭제된 경우
* 현재 사용자가 객체에 대한 충분한 접근 권한이 없는 경우 (보안 접근 규칙에 의해 정의됨)
* Entity가 [사용자 정의 동기화](#customizable-synchronization) 화면에서 XPath 제약 조건으로 구성되어 있고 객체가 더 이상 지정된 XPath 제약 조건과 일치하지 않는 경우
* Entity가 사용자 정의 동기화 화면에서 **Nothing (clear data)** 옵션으로 구성된 경우
* 업로드 단계에서 객체가 실패한 경우, 예를 들어 커밋 전 이벤트 핸들러가 false를 반환하거나 고유 유효성 검사 위반으로 인해 커밋이 실패한 경우

### 사용자 정의 동기화 {#customizable-synchronization}

{{% alert color="warning" %}}
이 설정은 [선택적 동기화](#selective-sync)에는 적용되지 않습니다.
{{% /alert %}}

기본적으로 Mendix는 [동기화](#synchronization)에서 언급한 대로 동기화해야 할 객체를 자동으로 결정합니다.

사용 사례에 따라 더 세밀한 동기화 제어가 필요할 수 있습니다. 따라서 Entity의 다운로드 동작을 변경할 수 있습니다. 다음 옵션 중에서 선택할 수 있습니다:

* **All Objects** — 일반 보안 제약 조건을 적용하여 모든 객체를 다운로드합니다
* **By XPath** — 일반 보안 제약 조건 외에 [XPath 제약 조건](/refguide8/xpath-constraints/)과 일치하는 객체만 다운로드합니다. 이는 XPath 제약 조건과 일치하지 않는 이전에 동기화된 모든 객체가 제거된다는 의미입니다.
* **Nothing (clear data)** — 객체를 자동으로 다운로드하지 않지만 동기화를 수행할 때 이 Entity에 대해 데이터베이스에 저장된 데이터를 지웁니다(객체를 업로드만 해야 하는 경우에 유용합니다. 예: `Feedback` Entity)
* **Nothing (preserve data)** — 객체를 자동으로 다운로드하지 않으며 동기화를 수행할 때 이 Entity에 대해 데이터베이스에 저장된 데이터를 지우지도 않습니다(동기화를 완전히 제어하려는 경우에 유용하며, 특정 객체가 선택된 [Synchronize to device](/refguide8/synchronize-to-device/) 또는 [Synchronize](/refguide8/synchronize/) 액티비티와 함께 사용해야 합니다)

오프라인 우선 프로필에서 Studio Pro가 감지할 수 없는 Entity를 사용하는 커스텀 위젯이나 JavaScript 액션이 있는 경우(코드에서만 사용되기 때문에), 사용자 정의 동기화를 사용하여 해당 Entity를 포함시킬 수 있습니다.

{{< figure src="/attachments/refguide8/mobile/offline-first/custom-sync.png" alt="custom synchronization"   width="450"  class="no-border" >}}

각 Entity에 대해 **Synchronization mode**가 표시됩니다. 기본값은 모델을 분석하여 자동으로 결정되지만, 개발자가 재정의할 수 있으며 이 경우 설정이 굵은 글씨로 표시됩니다.

### 제한 사항

유형(**전체** 또는 **선택적**)에 관계없이 여러 동기화 프로세스를 동시에 실행하는 것은 지원되지 않습니다. 자세한 내용은 *Synchronize 참조 가이드*의 [제한 사항](/refguide8/synchronize/#limitations) 섹션을 참조하세요.

### 오류 처리 {#error-handling}

동기화 중에 오류가 발생할 수 있습니다. 이 섹션에서는 Mendix가 이러한 오류를 처리하는 방법과 이를 방지하는 방법을 설명합니다.

#### 네트워크 관련 오류 {#network-errors}

동기화에는 서버 연결이 필요하므로 동기화 중에 네트워크 연결 실패 또는 불량으로 인해 오류가 발생할 수 있습니다. 네트워크 오류에는 연결 끊김이나 타임아웃이 포함될 수 있습니다. 기본적으로 하이브리드 모바일 앱의 동기화 타임아웃은 네트워크 요청당 30초입니다. 네이티브 앱의 경우 기본 타임아웃이 없으며, 타임아웃은 플랫폼과 OS 버전에 의해 결정됩니다.

동기화는 원자적(atomic)입니다. 즉, 모든 것이 동기화되거나 아무것도 동기화되지 않습니다. 예외 사항은 아래의 [모델 또는 데이터 관련 오류](#othererrors) 섹션에 설명되어 있습니다.

파일 업로드 중 네트워크 오류가 발생하면([업로드 단계의 2단계](#steptwo) 참조) Mendix는 실패한 파일을 다시 업로드하려고 시도합니다. 두 번째에도 오류가 발생하면 동기화가 중단됩니다. 해당 시점의 변경 사항은 로컬 디바이스에 유지되므로 나중에 다시 시도할 수 있습니다.

데이터 업로드 중 네트워크 오류가 발생하면([업로드 단계의 3단계](#stepthree) 참조) 데이터는 로컬 디바이스에 유지되며 서버에는 변경 사항이 적용되지 않습니다. [2단계](#steptwo)에서 업로드된 파일은 다음 동기화 시 다시 업로드됩니다.

데이터 업로드 후 네트워크 오류(예: 타임아웃)가 발생하면([업로드 단계의 3단계](#stepthree) 참조) 데이터는 로컬 디바이스에 유지됩니다. 그러나 서버가 이미 요청 처리를 시작했으므로 요청을 완료하고 서버 데이터베이스에 변경 사항을 커밋합니다. 디바이스는 서버가 요청을 처리했는지 여부를 구분할 수 없으므로 다음 동기화 시도에는 이미 적용된 변경 사항이 포함됩니다. 이 경우 서버는 Mendix 버전에 따라 다르게 동작합니다. Mendix Studio Pro 8.18 이하에서는 서버가 동일한 변경 사항을 다시 커밋하며, 이로 인해 두 동기화 사이에 다른 사용자가 수행한 변경 사항이 덮어써질 수 있습니다. Studio Pro 8.18 이상에서는 이 프로세스가 최적화되어 서버가 이미 적용된 변경 사항을 다시 커밋하지 않습니다.

다운로드 단계에서 네트워크 오류가 발생하면 디바이스의 데이터는 업데이트되지 않습니다. 따라서 사용자는 계속 작업하거나 다시 시도할 수 있습니다. 업로드 단계의 효과는 서버에서 롤백되지 않습니다.

동기화가 Nanoflow에서 호출된 경우 Nanoflow 오류 처리를 사용하여 오류를 처리할 수 있습니다. 다른 경우(예: 동기화가 버튼이나 시작 시 호출된 경우)에는 데이터를 동기화할 수 없다는 메시지가 사용자에게 표시됩니다.

#### 모델 또는 데이터 관련 오류 {#othererrors}

동기화 중에 변경되거나 새로운 객체가 커밋됩니다. 객체의 동기화는 다음과 같은 이유로 문제가 발생할 수 있습니다:

* 객체가 더 이상 서버에서 사용할 수 없는 경우 (삭제 또는 접근 규칙으로 인한 접근 불가)
* 접근 규칙으로 인해 객체의 멤버에 접근할 수 없게 된 경우
* 커밋 전/후 이벤트 Microflow 실행 중 오류가 발생한 경우
* 도메인 수준 유효성 검사 규칙에 따라 객체가 유효하지 않은 경우
* 객체에 댕글링 참조가 있는 경우 (자세한 내용은 아래의 [댕글링 참조](#dangling-references) 섹션을 참조하세요)

{{% alert color="warning" %}}위의 이유 중 하나로 동기화 오류가 발생하면 해당 객체의 커밋이 건너뛰어지고 변경 사항이 무시되며, 다른 객체에서 해당 객체에 대한 참조가 무효화됩니다. 건너뛴 객체를 참조하는 객체(오류를 트리거하지 않는 객체)는 정상적으로 동기화됩니다. 이러한 상황은 모델링 오류일 가능성이 높으며 서버에 기록됩니다. 데이터 손실을 방지하기 위해 해당 객체의 Attribute 값은 `System.SynchronizationError` Entity에 저장됩니다(Mendix 8.12부터).  {{% /alert %}}

#### 댕글링 참조 {#dangling-references}

동기화 중에 서버는 서버로 동기화되는 새 객체 또는 변경된 객체의 참조 무결성 유효성 검사를 수행합니다. 이 유효성 검사는 동기화된 객체 중 디바이스에만 존재하는 객체를 가리키는 Association이 없는지 확인합니다. Association이 이 조건을 만족하지 않으면 댕글링 참조입니다.

예를 들어, 커밋된 `City` 객체가 커밋되지 않은 `Country` 객체를 참조하는 경우, `City` 객체만 동기화하면 유효하지 않은 `Country` 객체 참조가 생성되며, 동기화 시 댕글링 참조 오류가 발생합니다.

댕글링 참조 오류는 모델링 오류입니다.

선택적 동기화 중 댕글링 오류를 방지하려면 동기화를 위해 선택된 모든 객체에 대해 디바이스에서 생성되었지만 아직 동기화되지 않은 다른 참조 객체도 동기화 대상으로 선택해야 합니다. 또는 이러한 객체를 먼저 동기화할 수 있습니다.

전체 동기화 중 댕글링 참조 오류를 방지하려면 동기화 전에 Association의 양쪽이 모두 커밋되었는지 확인하세요.

동기화된 객체 중 일부에 댕글링 참조가 있는 경우, 서버는 댕글링 참조가 있는 객체를 제외한 다른 모든 객체를 동기화합니다. 댕글링 참조가 있는 객체에 대해 서버는 동기화 오류를 생성하고 `System.SynchronizationError` Entity에 저장합니다. 이러한 상황에서는 다음과 같은 오류 메시지를 볼 수 있습니다:

```text
Synchronizing an object of type City with GUID {123} has failed due to a modelling error. The object has a reference to other objects (City_Country) that have not been synchronized to the runtime yet. This breaks referential integrity of the object because it references a non-existing object in the runtime database. Please make sure that you synchronize the referenced object together with the City or before synchronizing the City.
```

데이터 손실을 방지하기 위해 오류 객체에는 오류를 일으킨 객체의 데이터에 대한 JSON 표현이 포함되어 있습니다.

### 동기화 문제 방지 {#prevent-sync-issues}

위에서 언급한 문제를 방지하기 위해 Mendix는 다음 모범 사례를 따를 것을 권장합니다:

* 초기 릴리스 후 오프라인 앱에서 Entity 또는 해당 Attribute의 유형을 제거, 이름 변경 또는 변경하지 마세요 — 이로 인해 오프라인 사용자가 객체나 값에 더 이상 접근할 수 없게 될 수 있습니다(필요한 경우, 여전히 이전 버전과 호환되는 "중간" 릴리스를 수행한 후 모든 앱이 동기화된 후 다음 릴리스에서 변경할 수 있습니다)
* 오프라인 사용자에게 동기화될 수 있는 객체를 삭제하지 마세요 (동기화하려고 할 때 해당 객체의 변경 사항이 손실됩니다)
* 오프라인 Entity에 도메인 수준 유효성 검사를 사용하지 마세요 — 대신 Nanoflow 또는 입력 유효성 검사를 사용하세요 (Microflow를 사용하여 서버에서 다시 유효성 검사를 수행하는 것도 좋은 관행입니다)
* 다른 객체에 의해 참조되는 객체를 커밋할 때 다른 객체도 커밋되었는지 확인하세요

Nanoflow에서 동기화 액션을 사용하여 동기화가 트리거되고 오류가 발생하면 Nanoflow 오류 처리를 사용하여 오류를 우아하게 처리할 수 있습니다.

### 충돌 해결 {#conflict-res}

여러 사용자가 디바이스에서 동일한 상태의 객체를 동기화하고, 변경한 후, 이 객체를 서버로 다시 동기화하는 일이 발생할 수 있습니다. 이 경우 마지막 동기화가 서버의 객체 전체 내용을 덮어씁니다. 이를 "마지막 승리(last wins)" 접근 방식이라고도 합니다.

다른 접근 방식이 필요한 경우, 커밋 전 Microflow에서 충돌을 감지할 수 있습니다(예: Entity의 리비전 ID Attribute 사용). 이를 기반으로 사용자 정의 충돌 해결을 수행할 수 있습니다.

## 모범 사례 {#best-practices}

Mendix 애플리케이션에서 최상의 사용자 경험을 보장하려면 다음 모범 사례를 따르세요:

* 동기화 구성 또는 보안 접근 규칙을 사용자 정의하여 동기화될 데이터의 양을 제한하세요
* 네트워크 연결이 느리고 불안정할 수 있으며 모바일 디바이스의 저장 공간이 제한적인 경우가 많으므로, 대용량 파일이나 이미지의 동기화를 피하세요 (예: 사진 크기 제한)
* UI 요소 대신 Nanoflow를 통해 동기화하여 동기화 실패 시(연결 오류, 모델 및 데이터 관련 오류 등) 처리할 수 있는 오류 처리를 동기화 액티비티에 추가하세요
* 선택적 동기화를 사용하여 대용량 파일이나 이미지를 동기화하세요
* 서버에서 충돌을 올바르게 처리할 수 있도록 삭제 기능에 `isDeleted` Boolean Attribute를 사용하세요
* 데이터를 사전 또는 사후 처리하기 위해 커밋 전/후 Microflow를 사용하세요
* Nanoflow에서 [Microflow 호출](/refguide8/microflow-call/)을 사용하여 REST 서비스에서 데이터를 검색하거나 Java 액션과 같은 복잡한 로직에 접근하고 사용하는 등의 추가 서버 측 로직을 수행하세요
* 데이터가 가능한 한 빨리 처리되도록 사용자에게 데이터 동기화를 상기시키세요: 객체를 커밋하는 Nanoflow에서 연결을 확인하고 자동으로 동기화하거나, 알림을 사용하여 동기화하도록 사용자에게 알리거나, 로그아웃 전에 동기화하여 데이터가 손실되지 않도록 하세요

## 앱이 오프라인 우선인지 확인하기 {#limitations}

Mendix는 개발자가 풍부한 오프라인 우선 앱을 구축할 수 있도록 도와줍니다. 그러나 몇 가지 제한 사항이 있습니다.

### Microflow {#microflows}

Microflow는 Nanoflow에서 [Microflow 호출](/refguide8/microflow-call/) 액션을 사용하여 오프라인 앱에서 호출하여 서버에서 로직을 수행할 수 있습니다. 그러나 온라인 프로필에서 사용할 때와는 약간 다르게 작동하며, 이러한 차이점은 아래에서 설명합니다:

#### Microflow 인수 유형

* 영속성 Entity의 객체 또는 목록을 전달하는 것은 지원되지 않습니다.
* 영속성 Entity와 Association이 있는 비영속성 Entity의 객체 또는 목록을 전달하는 것은 지원되지 않습니다(이러한 Association은 간접적인 Association일 수 있습니다).
* 다른 Microflow에서 생성된 비영속성 Entity를 전달하는 것은 지원되지 않습니다.

#### UI 액션

UI 관련 액션은 무시되며 아무런 효과가 없습니다. 이러한 UI 관련 부작용은 호출하는 Nanoflow에서 모델링하는 것을 권장합니다.

이러한 액션은 다음과 같습니다:

* [Show message](/refguide8/show-message/)
* [Show validation message](/refguide8/validation-feedback/)
* [Show home page](/refguide8/show-home-page/)
* [Show page](/refguide8/show-page/)
* [Close page](/refguide8/close-page/)
* [Download file](/refguide8/download-file/)

#### 객체 부작용

Microflow에서 영속성 객체에 대한 변경 사항은 동기화하지 않으면 클라이언트에 반영되지 않습니다. 변경 사항이 반영되려면 비영속성 객체를 반환해야 합니다.

#### Microflow 반환값

* 영속성 Entity의 객체 또는 목록을 반환하는 것은 지원되지 않습니다.
* 영속성 Entity와 Association이 있는 비영속성 Entity의 객체 또는 목록을 반환하는 것은 지원되지 않습니다(이러한 Association은 간접적인 Association일 수 있습니다).

#### 언어 전환

Mendix 앱의 언어를 전환하려면 디바이스가 온라인 상태이고 Mendix 런타임에 접근할 수 있어야 합니다. 런타임에 대한 자세한 내용은 [런타임 참조 가이드](/refguide8/runtime/)를 참조하세요.

### 오프라인 Microflow 모범 사례 {#offline-mf-best-practices}

오프라인 우선 앱에서 Microflow 호출이 작동하도록 하기 위해 Mendix는 오프라인 앱에 일부 Microflow 정보를 저장합니다. 해당 정보는 앱에서 호출됩니다. 이는 오프라인 앱에서 사용되는 Microflow에 대한 변경이 이전 버전과 호환되어야 함을 의미합니다. 아직 OTA(Over the Air) 업데이트를 받지 못한 이전 앱이 있을 수 있기 때문입니다. 이러한 디바이스에서의 모든 Microflow 호출에는 Nanoflow의 이전 Microflow 호출 구성이 여전히 포함되어 있으므로 요청이 실패할 수 있습니다. OTA 업데이트에 대한 자세한 내용은 [Over the Air 업데이트 사용 방법](/howto8/mobile/how-to-ota/)을 참조하세요.

초기 릴리스 후 오프라인 Microflow 호출에서 이전 버전과의 호환성 오류를 방지하기 위해 Mendix는 다음 모범 사례를 권장합니다:

* Microflow의 이름을 변경하거나 다른 모듈로 이동하지 마세요
* 오프라인 앱에서 호출되는 Microflow가 포함된 모듈의 이름을 변경하지 마세요
* Microflow 매개변수를 추가, 제거, 이름 변경 또는 유형 변경하지 마세요
* 반환 유형을 변경하지 마세요
* 모든 디바이스가 업데이트를 받았는지 확인하기 전에 Microflow를 삭제하지 마세요

위에 설명된 관행에서 벗어나려면 새 Microflow를 도입하세요. Microflow의 내용은 변경할 수 있지만, 이전 앱이 업데이트될 때까지 새 버전의 Microflow를 호출할 수 있다는 점에 유의하세요.

### 자동 번호 및 계산된 Attribute {#autonumbers}

자동 번호와 계산된 Attribute는 모두 서버의 입력이 필요하므로 허용되지 않습니다. 이러한 Attribute 유형을 가진 객체는 오프라인에서 여전히 보고 생성할 수 있지만, Attribute 자체는 표시할 수 없습니다.

### 기본 Attribute 값 {#default-attributive}

Domain Model에서 Entity의 기본 Attribute 값은 오프라인에서 생성된 객체에 영향을 미치지 않습니다. Boolean Attribute는 항상 `false`로, 숫자 Attribute는 `0`으로, 기타 Attribute는 `empty`로 기본 설정됩니다.

### 다대다 Association {#many-to-many}

다대다 Association은 지원되지 않습니다. 일반적인 대안은 다른 Entity와 일대다 Association을 가진 세 번째 Entity를 도입하는 것입니다.

### 상속 {#inheritance}

일반화(Generalization) 또는 특수화(Specialization) 관계에서 둘 이상의 Entity를 사용하는 것은 불가능합니다. 예를 들어 `Animal` Entity와 `Dog` 특수화가 있는 경우, 오프라인 프로필에서 `Animal` 또는 `Dog`를 사용할 수 있지만 둘 다 사용할 수는 없습니다. 대안 패턴은 구성(Composition)을 사용하는 것입니다(예: 객체 Association).

### 시스템 멤버 {#system-members}

시스템 멤버(`createdDate`, `changedDate`, `owner`, `changedBy`)는 지원되지 않습니다.

### Excel 및 CSV 내보내기 {#excel-cv}

오프라인 애플리케이션에서는 Excel 및 CSV 내보내기를 사용할 수 없습니다.

### 해시된 문자열 Attribute {#hashed-strings}

해시된 문자열 [Attribute 유형](/refguide8/attributes/#type)을 가진 Attribute는 동기화되지 않습니다.
