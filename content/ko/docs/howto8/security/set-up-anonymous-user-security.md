## 소개

애플리케이션에 대한 익명 접근을 설정할 때 사용자에게 접근 권한을 부여하는 위치에 주의해야 합니다. 전체 애플리케이션을 대중에게 접근 가능하게 만들지 않도록 몇 가지 가이드라인이 있습니다.

익명 사용자 역할을 만들 때 항상 가능한 한 적은 접근 권한을 부여하십시오. 따라서 명명된 사용자 계정의 모듈 규칙을 재사용해서는 안 됩니다. 모듈 규칙을 재사용하는 것이 더 빠를 수 있지만, 이렇게 하면 익명 사용자에게 애플리케이션의 정보에 대한 과도한 접근 권한을 부여하기가 훨씬 쉬워집니다. 익명 사용자를 사용할 때, 객체에 대한 변경 사항은 사용자가 익명이고 더 이상 존재하지 않으므로 실제 사용자로 추적할 수 없습니다.

**이 사용 방법 가이드를 사용한 후 다음을 수행하는 방법을 알게 됩니다:**

* 비영속 객체에 대한 접근 설정하기
* 익명 사용자에게 읽기 및 쓰기 접근 권한 부여하기

## 비영속 객체

비영속 객체에 대한 접근을 설정할 때, 지정하는 보안 규칙은 기능적으로 필요한 것이어야 합니다. 비영속 객체는 객체를 만든 사용자의 세션 캐시에서만 존재하므로, 익명 사용자는 특별히 그들을 위해 또는 그들에 의해 생성되지 않은 정보에 접근할 수 없습니다. 그러나 영속 객체의 경우는 완전히 다른 상황입니다.

## 쓰기 접근

애플리케이션의 어떤 필드에든 익명 사용자에게 쓰기 접근 권한을 부여하는 경우 인스턴스 접근도 지정해야 합니다. 익명 사용자가 특정 객체 유형의 모든 레코드를 변경하는 것이 허용되는 경우는 거의 없습니다. 익명 사용자는 일반적으로 방금 만든 레코드만 변경할 수 있으므로 다음 접근 규칙을 지정하는 것이 좋습니다: `[System.Owner='[%CurrentUser%]']` 이렇게 하면 익명 사용자는 세션 중에 방금 만든 레코드만 변경할 수 있습니다.

## 읽기 접근

익명 사용자가 특정 기본 데이터 테이블에 접근해야 하거나 개요에서 사용자 이름이 필요한 경우 해당 Entity에 대한 읽기 접근 권한이 필요합니다. 그러나 항상 이 접근을 제한해야 합니다. 사용자가 모든 필드에 접근할 필요가 없다면 부여하지 마십시오. 전체 읽기 접근 권한이 있는 익명 사용자를 보면 항상 더 적은 접근 권한으로 작동할 수 없는지 확인하십시오.

## 보안 검토

애플리케이션을 검토하고 익명 사용자를 검토할 때 가장 자주 위험 신호를 트리거하는 세 가지가 있습니다 (애플리케이션이 안전하지 않음을 나타냄):

* 일반 애플리케이션 사용자의 모듈 역할을 재사용하는 익명 사용자 역할
* 쓰기 접근 권한이 있지만 인스턴스 접근 XPath 제약 조건이 없는 익명 모듈 역할
* Entity에 대한 전체 읽기 접근 권한이 있는 익명 모듈 역할

이러한 상황 중 하나라도 보이면 달성하려는 목표에 이러한 매개변수가 필요한지 신중하게 고려해야 합니다.

**페이지에서 데이터를 제한하는 것은 애플리케이션을 안전하게 만들지 않습니다.** 애플리케이션을 안전하게 만드는 유일한 방법은 모든 Entity에 접근 규칙을 지정하고 볼 수 있는 객체의 인스턴스를 제한하는 것입니다.

모든 사용자는 URL에 메시지를 게시할 수 있는 도구를 다운로드하고 플랫폼에 JSON 쿼리를 보내려 시도하여 API와 직접 통신할 수 있습니다. 이는 브라우저와 서버 간의 통신을 시뮬레이트하는데, 서버는 메시지가 세션 내에서 허용된 것과 일치하는 한 누가 보내든 상관하지 않습니다.

## 모범 사례

익명 접근이 있는 경우 가능한 한 적은 수의 Entity에 대한 접근을 제한하고, 단지 항목을 선택하기 위한 것이라면 모든 Attribute에 대한 전체 읽기 접근 권한을 부여해서는 안 됩니다. 예를 들어, 익명 사용자가 프로젝트 이름을 볼 수 있어야 하는 경우 전체 Entity가 아닌 프로젝트 이름에만 읽기 접근 권한을 부여하십시오.

익명 사용자에게 객체를 변경할 수 있는 접근 권한을 부여해야 하는 경우 항상 인스턴스 접근도 적용하십시오. 익명 사용자는 Entity의 모든 레코드에 대한 쓰기 접근 권한을 가져서는 안 됩니다.

내비게이션 또는 페이지 표시를 제한하는 것은 보안과 같은 것이 아닙니다. 모든 데이터는 Platform API에 직접 통신하여 접근할 수 있으며, 보안 모델에 따라 보이는 모든 것은 서버에 올바른 메시지를 보내 접근할 수 있습니다. UI에서 데이터를 제한한다고 해서 접근할 수 없는 것이 아닙니다. 인스턴스 접근 규칙만이 무엇을 할 수 있고 할 수 없는지를 보장합니다.
