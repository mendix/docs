## 소개

Mendix에서 만든 Solution이나 컴포넌트를 판매하고 고객이나 파트너가 모델에 액세스할 수 있는 경우, 해당 콘텐츠의 지적 재산(IP)을 보호하는 것을 고려해야 합니다. 또한 개발자가 의도한 대로 구현을 사용하도록 보장하고, 고객이 실수로 또는 의도적으로 비활성화할 수 없도록 사용자 지정 사용량 측정을 보호하려고 합니다. 따라서 Solution과 컴포넌트에 최소한 일부 IP 보호를 적용하는 것이 좋습니다.

## IP 보호의 중요성

재사용 가능한 Solution, App Service, 커넥터 및 기타 모듈에는 Microflow와 같은 앱 모델 콘텐츠 형태의 IP가 포함되어 있습니다. 이 재사용 가능한 콘텐츠는 수익화할 수 있습니다. 이러한 유형의 판매 가능한 콘텐츠를 기반으로 비즈니스를 구축할 때 IP 손실과 관련된 위험이 있습니다. 고객이 게시자에게 보상하지 않고 IP를 복사하면 잠재적 수익의 일부를 잃게 됩니다.

따라서 이러한 콘텐츠를 배포할 때, 모듈에 잘 설계된 API를 통해 기능을 사용할 수 있도록 하면서 고객에게 구현의 일부를 숨기는 것이 권장됩니다. 이는 명시적으로 정의된 Microflow, Nanoflow 및 Entity를 가지고 있으면서 다른 모든 문서와 내부 관심사는 숨기는 것을 의미합니다.

IP 보호 개념을 적용하여 모듈이 실수로 또는 의도적으로 수정되는 것을 방지할 수도 있습니다. 이 경우 금전적 이유로 IP를 보호하는 것이 아니라, 기능이 의도한 대로 사용되도록 보장하기 위해 IP를 보호하는 것입니다. 이는 유지 관리 및 업그레이드 경로를 간소화하는 데 도움이 됩니다. 이는 애플리케이션 모델이 외부 당사자와 공유되는지 여부에 관계없이 관련이 있습니다.

## 기술적 제한 위에 법적 프레임워크 사용

IP 보호와 [Solution 모듈](/refguide/module-settings/#solution-module)을 사용하면 구현이 Studio Pro와 Model SDK에서 숨겨집니다. 이를 통해 IP를 보호하고 다른 사람이 복제하는 것을 방지할 수 있습니다. 그러나 이는 사람들이 특정 로직이 어떻게 구축되었는지 리버스 엔지니어링하거나 액세스 가능한 애플리케이션 부분을 분석하는 것을 방지하지는 않습니다. 따라서 IP를 보호하기 위한 적절한 이용 약관을 마련하여 오용에 대응할 수 있도록 하십시오.

## 보호해야 할 콘텐츠

[적응성](/appstore/creating-content/sol-adapt/#three-parts)을 허용하기 위해 Solution이나 컴포넌트의 모든 부분을 보호할 필요는 없습니다. Mendix는 다음을 보호할 것을 권장합니다:

* **Solution의 핵심 IP** – 보호가 필요한 비즈니스 로직(예: 스케줄링 또는 계획 알고리즘), 복잡한 데이터 매핑, 비즈니스 규칙 및 의사 결정 로직을 분석하십시오.
* **사용자 지정 사용량 측정** – 실수로든 의도적으로든 측정이 변조되지 않도록 보장하십시오.
* **라이선스 관리** - 유효한 구독에 대해 Solution의 사용을 제어합니다.
* **고객이 절대 수정해서는 안 되는 Solution의 모든 부분** – API 뒤에 구현 세부 사항을 숨겨 확장에 집중하는 고객이나 구현 팀이 구현 세부 사항에 방해받지 않도록 하십시오.

## 효과적인 IP 보호 적용

### 아키텍처 설계 모범 사례

* 핵심 IP를 식별하십시오:
    * Solution에서 가장 중요한 부분이 무엇인지 생각하십시오.
    * 고객이 조정할 부분이 무엇인지 생각하십시오. 해당 부분은 보호할 수 없습니다.
* API를 정의하십시오:
    * IP 보호된 콘텐츠의 API를 식별하십시오.
    * 확장 요구를 고려하되, 간단하게 유지하십시오.
    * 모든 것을 지원하기 위해 과도하게 엔지니어링하는 대신 제한된 기능 세트의 간단한 인터페이스를 만드십시오.   
    * 많은 옵션이 있는 API를 정의하는 것을 자제하십시오. 사용하기가 훨씬 어렵습니다.
    * API 노출을 제한하십시오. 나중에 더 추가하는 것이 인터페이스를 축소하는 것보다 쉽습니다.
    * 명확성을 위해 적절한 이름 지정과 간단한 문서를 적용하십시오.
    * 적절한 유효성 검사 및 오류 처리를 통해 비정상 흐름을 고려하십시오.

자세한 내용은 [적응 가능한 Solution 아키텍처 설계](/appstore/creating-content/sol-architecting/)를 참조하십시오.

### 구현 숨기기의 이점 {#implementation}

#### 게시자의 경우

Mendix는 IP를 보호하기 위한 수단으로 모듈 구현의 숨기기를 지원합니다. 게시자는 앱 모델의 어떤 부분이 표시되고 편집 가능한지, 어떤 부분이 소비자에게 숨겨지는지를 제어할 수 있습니다.  

숨겨진 모델 문서와 요소 위에 API를 정의하여 앱의 다른 부분에서 기능을 재사용하고 확장할 수 있도록 할 수 있습니다.

이를 통해 적응 가능한 Solution은 모든 고객 간에 공유되는 [공통 코어](/appstore/creating-content/sol-architecting/#app-design)를 보호하면서 그 위에 조정 가능한 셸을 둘 수 있습니다. 조정 가능한 셸은 커스터마이즈 가능한 코어에 모델 변경을 하거나 완전히 새로운 모듈로 앱을 확장하여 각 고객에 맞게 커스터마이즈됩니다. 커스터마이제이션과 확장 모두 공통 코어의 API를 활용합니다.

#### 소비자의 경우

이러한 종류의 IP 보호가 적용된 Solution의 소비자는 잘 설계된 API만 볼 수 있습니다. 이는 다음과 같은 결과를 가져옵니다:

* 커스터마이제이션이 간소화되고 확장 방법과 위치가 명확해집니다. 고객은 해당 API만 알면 되며, 확장 방법과 위치가 명확해집니다.
* App Service, 커넥터 및 기타 모듈의 사용이 간소화됩니다. 구현 세부 사항이 숨겨져 있기 때문입니다.
* 유지 관리 노력이 줄어듭니다. 숨겨진 콘텐츠는 변경할 수 없기 때문입니다. 이는 커스터마이제이션이 적용되었는지 확인할 필요가 없으므로 인플레이스 업그레이드를 더 쉽게 만듭니다.

### 컴포넌트 유형 보호

#### 적응 가능한 Solution

고객, 타사 구현 파트너 또는 자체 전문 서비스 팀이 커스터마이즈하는 적응 가능한 Solution은 IP 보호의 혜택을 받을 수 있습니다. 고객 간에 공유되는 공통 코어를 보호함으로써 유지 관리 노력을 통제하고, 실수로 또는 의도적인 변경으로부터 코어를 보호합니다.

Solution을 보호하려면 Mendix는 다음 단계를 권장합니다:

1. 고객 간에 변경되지 않는 공유 [공통 코어](/appstore/creating-content/sol-adapt/#three-parts)를 식별하고 보호합니다.
2. 고객이 조정하려는 유연한 셸을 구성하는 부분을 식별합니다.
3. 공통 코어와 유연한 셸 사이에 명확한 API를 정의합니다. 이를 통해 코어를 조정할 필요가 없고 제한된 노력으로 확장할 수 있는 좋은 아키텍처를 보장합니다.

이러한 경계를 처음에 올바르게 정의하기가 매우 어려울 수 있으므로 반복적으로 접근하십시오. 대신 가능한 한 적게 공개하고 점진적 릴리스를 통해 API 노출을 늘리십시오.

#### 전체 Solution 모델

Mendix 모델이 어떻게 설계되었는지(Solution Module 포함 여부)에 관계없이, MDA를 고객과 공유하면 항상 구현을 숨길 수 있습니다. 이를 통해 Mendix 모델을 열 수 없게 하면서 사용자 지정 배포가 가능합니다.

#### App Service, 커넥터 및 모듈

Marketplace에서 사용할 수 있는 App Service, 커넥터 및 모듈에는 종종 지적 재산과 사용자 지정 [사용량 측정](#metering)이 포함됩니다. 해당 콘텐츠를 보호하는 것이 중요합니다.

또한 [구현 세부 사항 숨기기](#implementation)는 해당 앱에서 App Service, 커넥터 및 모듈을 사용하는 개발자의 작업을 간소화할 수 있습니다.

App Service, 커넥터 및 모듈을 보호하려면 다음 단계를 따르십시오:

1. 고객을 위한 API 설계부터 시작하십시오. 잠재 고객과 함께 검증하십시오. 그들이 어떻게 사용할지 가정하지 마십시오.
2. 약 80%의 사용 사례를 다루기 위해 원하는 API의 합의된 하위 집합을 구현하십시오.
3. "API 뒤의 것을 보호" 원칙을 적용하십시오. API 뒤에서 일어나는 일에 대한 고객의 우려를 해소하기 위해 IP 보호를 적용하십시오.
4. 전체 모듈이나 모듈 세트에 IP 보호를 적용하지 않는 경우, 최소한 사용자 지정 사용량 측정을 구현하는 모듈을 보호하십시오. 이는 고객의 실수로 또는 의도적인 변조를 방지합니다.

### 사용량 측정 보호 {#metering}

고객이 실수로 또는 의도적으로 사용량 측정을 중단하지 않도록 하기 위해, 사용자 지정 사용량 측정의 구현을 보호된 모듈에 숨기는 것이 좋은 관행입니다.

사용자 지정 사용량 측정에는 두 가지 일반적인 시나리오가 있습니다:

* **Solution에서 관리하는 자산 추적** – 자산이 도메인 모델의 Entity로 관리되는 경우, 예약 이벤트를 사용하여 정기적인 간격으로 관리되는 자산 수를 추적하는 게이지 메트릭을 사용할 수 있습니다.
* **API 또는 UI를 통해 Solution에서 처리하는 트랜잭션 수 계산** – 트랜잭션이 호출될 때마다 일정 기간 동안 처리된 총 트랜잭션 수를 추적하는 증분 카운터 메트릭을 사용할 수 있습니다.

다음은 사용량 측정에 대한 모범 사례입니다:

* 사용량 측정이 올바른 쪽에 있고 API 뒤에 숨겨져 있는지 확인하십시오.
* 사용량 측정이 API의 특정 호출에 의존하지 않도록 하십시오.    
  정기적인 간격의 사용량 측정을 시작하기 위해 after-startup Microflow에 의존하는 것은 실수로 비활성화될 수 있으므로 좋은 방법이 아닙니다.
  그러나 after-startup Microflow가 기능적 목적(예: 사용자 지정 요청 핸들러 시작 또는 모듈 초기화)에도 사용되는 경우 안전하게 사용할 수 있습니다.
* Solution 또는 App Service에 대한 법적 계약을 마련하십시오. 여기에는 고객이 사용자 지정 사용량 측정이 의도한 대로 작동하도록 보장해야 한다는 조항이 포함되어야 합니다.
  이는 어떤 이유로 기술적 수준에서 측정 구현을 보호할 수 없는 경우에도 법적 수준에서 보호받을 수 있음을 의미합니다.

### 라이선스 관리

IP 보호를 적용하면 Solution을 사용하는 사람들이 모델의 세부 사항을 검사하고 구현을 복사하는 것을 방지합니다. 이 외에도 Mendix는 라이선스 관리를 구현할 것을 권장합니다.

모든 구현에는 암호화로 서명된 라이선스 키가 있을 수 있으며, 이를 통해 애플리케이션이 구현에 사용할 수 있는 라이선스가 무엇인지 검증할 수 있습니다. 이는 오용을 방지하고 다음과 같은 기능을 활성화할 수 있습니다:

* *localhost*에서의 무료 제품 평가
* *.mxapps.io*에서 Free App을 사용한 프리미엄 모델
* 특정 기능을 활성화하거나 특정 작업을 속도 제한하여 제품의 여러 에디션 제공
* 시간에 따른 라이선스 키 만료
* 특정 런타임 URL에 대한 라이선스 키 유효성
